## [Unreleased]

### Fixed

- **kiro radio was never wired up at all: the hooks were written to a directory `kiro-cli` does not read, so no kiro role had ever registered (#218).** `task-init` wrote `radio-register` / `radio-busy` / `radio-ready` into `<repo>/.kiro/hooks/*.json`. That is the **Kiro IDE**'s agent-hooks location; `kiro-cli` — what the loadouts actually launch — reads hooks from the `hooks` field of each agent config, and the string `.kiro/hooks` does not appear in its binary. So none of the three had ever run: no `agentSpawn` register, no `userPromptSubmit` state flip, no idle flip at end of turn. Every `radio send` to a kiro role returned `no session … message queued`, in both directions, and every handoff needed a human courier. Six months of logs contain exactly one `agent=kiro` register line, and it was hand-typed (its `--loadout` and `--repo` are empty, which the hook never leaves blank). Two further defects were folded into the same shape: `agentStop`, the trigger `radio-ready` used, is **not a valid kiro-cli trigger** — an agent config carrying one fails to load wholesale — and the `{"trigger":…,"action":{"type":"shellCommand",…}}` entry form is rejected inside an agent config, which takes `{"command": …}`. All three hooks now merge into `.kiro/agents/*.json` on `agentSpawn` / `userPromptSubmit` / `stop` (verified per-turn against kiro-cli 2.24.0). The merge runs regardless of the overwrite policy and only adds an entry when no command on that trigger already starts with `radio `, so a repo whose customized agent file is *kept* still comes out with working hooks — that upgrade path is the point — while pre-existing non-radio hooks survive. A re-run also sweeps the inert `.kiro/hooks/radio-*.json` it used to write, leaving any hook of your own in that directory alone. What was never broken: the zellij wake itself, which the logs show working on kiro whenever a session file happened to exist.

  The three kiro `_radio_install_hooks` bodies were triplicated with **no** `check-drift` sentinel, and had already diverged — `kiro-local` / `kiro-notion` hard-coded their loadout name where `kiro-gh` used the `${TASK_FORCE_LOADOUT:-…}` override form. All three now use the override form and are drift-guarded by four new regions, and `kiro-local` / `kiro-notion` get hook tests for the first time.

  Upgrading: **re-run `task-init kiro-<tracker>`.** The fix lives entirely in installer-written artifacts; nothing self-applies.

- **kiro *does* inject hook stdout into the model's context — the docs said the opposite in seven places, and one test enforced it (#218, follow-up #221).** The claim was inferred from never observing injection, which had the same single cause as everything above: the hooks were never running. Verified with a nonce control on kiro-cli 2.24.0 — a `userPromptSubmit` hook echoed a random value never present in the prompt, and the model reproduced it exactly. Corrected in `README.md`, `.claude/gh-workflow.md` and the seven `*/steering/*-workflow.example.md` templates, in two `bin/radio` comments, and in `tests/kiro_radio_pull.bats`, which asserted the false string and so pinned it in place. The citations were also wrong: all of them pointed at #146, which is about `task-reviewer` migrating to `SPEC_IDENTIFIER` and has nothing to do with context injection — so the claim had been riding a bogus issue number and had no tracking issue at all. They now point at **#221**, which carries the re-derivation this unblocks: `prompt-hook`, the register drain, whether `stop` honours block JSON (untested — a different contract from stdout injection), and whether #190's "declare kiro best-effort" decision still holds. No behaviour changed here: kiro keeps `radio busy` rather than `prompt-hook` pending that call.

- **A cold `radio register` could write an empty `TAB_ID`, leaving a role permanently unwakeable (#218).** `_info_file_tab_id()` — the #188 fallback that recovers the id from `<worktree-base>/.<slug>.info`, which `task-work` owns and radio never writes — was wired into the re-seed path and nowhere else. `cmd_register` had only the #117 preserve-from-existing-session branch, so a *first* register with no prior session file and a missed `zellij list-tabs` lookup wrote `TAB_ID=`, and `cmd_send` then queued every later message with no wake attempt at all. Squarely on #218's path: once kiro roles register, the first register each one performs is a cold one. `cmd_register` now falls back the same way the re-seed does and logs `tab_id_src=zellij|session-preserved|info-file|none`, with the unbound case getting its own greppable line.

- **The kiro launchers now refuse to spawn an agent that does not resolve (#218).** `kiro-cli chat --agent <name>` does not fail on an unknown agent: it prints one io error to stderr, instantly scrolled past by the TUI it then starts, and falls back to a built-in default carrying none of task-force's hooks — so radio goes dead for the whole session and looks like a radio bug. This arrives as a stale install rather than a missing one, because `~/.kiro/agents/*.json` are symlinks into the checkout that installed them: rename or move that checkout and every link dangles. `bin/task-pm` and the three `kiro-*/bin/task-work` (plus `kiro-gh/bin/task-reviewer`) now check the agent resolves via new `lib/kiro-agent.sh` before doing anything — for `task-pm` before the tab rename (#165 RC-6), for `task-work` before the worktree, branch and tab exist — and a dangling symlink is reported as dangling, with its target, rather than as merely absent.

- **`task-board` gets a root dispatcher: present on every loadout, refusing with an explanation where it does not apply (#215).** It was the only task-force command with no `bin/<cmd>` dispatcher — `claude-local/install.sh` and `kiro-local/install.sh` each symlinked `~/.local/bin/task-board` straight at their own copy. Three consequences, all live: on a `claude-gh` / `jira` / `notion` repo the command was simply **absent** (`command not found`, indistinguishable from a broken install — which is how this was found); installing both local loadouts left whichever ran last owning the symlink, the same class as #20; and the two byte-identical copies had **zero** `tools/check-drift.sh` manifest entries, so a fix landing in one and not the other was exactly the failure mode the drift check exists to catch, unwatched. `bin/task-board` now follows the same shape as its five siblings (symlink-resolution → `AW_ROOT` → `aw_detect_impl` → `exec`), every loadout links it, and on a non-local loadout it exits non-zero naming the detected loadout and where that repo's board actually lives. It is local-only **by design** — it renders `tasks/_board.md` out of local task-file frontmatter — so the fix is a dispatcher that says so, not a per-tracker board view. Detection follows `--repo PATH` when given, because `task-work` and `task-done` call `task-board` that way from a worktree. The two copies are now drift-guarded by a `board-render` region.

  Upgrading: re-run `task-init <loadout>`? Not needed — no `task-init`-written artifact changed. Re-run the **installer** (`./install.sh <loadout>`) to pick up the `~/.local/bin/task-board` link; on a local loadout that also repoints an existing symlink from the impl copy to the dispatcher.

- **The `#198` pty tests no longer fail for a reason that has nothing to do with radio: `pty_run` pins the fd it hands `script` instead of inheriting the caller's stdin (#207).** `script` allocates the pty for its *child*, but first calls `tcgetattr()` on its own fd 0 to copy the invoking terminal's attributes. A tty succeeds; a pipe or `/dev/null` yields `ENOTTY`, which `script` tolerates; a **socket** yields `EOPNOTSUPP`, which BSD `script` does not — it aborts with `script: tcgetattr/ioctl: Operation not supported on socket` and `run pty_run …` records that as the command under test failing. An agent harness wires its child's stdin to a socket on some invocations and to a character device on others, which is why the three `unregister … from a terminal` tests in `tests/radio_lifecycle.bats` went red under a worker, passed on a re-run, and stayed green on both CI runners. A test that goes red for reasons unrelated to what it asserts is worse than no test: it trains whoever runs the suite to discount red, which is the habit that let #194's suppressed CI run pass for green.

  `pty_stdin` now names `/dev/tty` where the host has a controlling terminal and `/dev/null` otherwise, and `pty_run` redirects from it — `script` still allocates a genuine pty for the child either way, so `[[ -t 0 ]]` inside the command under test stays TRUE and the #198 tty branch is still really exercised, including on both CI runners. Nothing is skipped away: verified green under a manufactured socket stdin (1131/1131, zero skips), and under pipe and `/dev/null` stdin. A new `require_pty` guards the three tests for the host that genuinely cannot allocate a pty — it probes for one and requires the child to confirm it, then `skip`s **naming the reason**, since a silent skip makes "not run" and "passed" identical in the summary. `pty_run` also strips the `^D` the pty echoes when `script` closes its input, which would otherwise prefix the child's first line. New `tests/pty_helper.bats` covers the helper itself, socket-stdin case included.

  Upgrading: no `task-init` re-run needed — test-harness only, no installed artifact changes.

- **`task-init` no longer offers to delete the repo-specific sections you were told to put in `.claude/<loadout>-workflow.md` — the workflow doc is now installed as a *managed region*, and a re-run replaces only what is between the markers (#183).** #177 deliberately routes repo-specific guidance (the "in this repo, Green means `./run_tests.sh` + `check-drift.sh`" gloss) into this file, while every CHANGELOG entry since #163 tells users to re-run `task-init <loadout>` to pull updated hooks and prompts. Those two instructions collided inside `install_file`, whose policies are whole-file: a re-run could keep the user's edits or clobber them, never both. It clobbered — three times on this repo's own copy, most recently local commit `4c3e11f`, a 20-line pure deletion of the "Pre-PR checklist (this repo)" section that `tests/worker_checklist.bats` greps for. The suite went red on `main`; the commit carried a CI-skip marker (#194) so no run ever executed against it, and **three separate workers** independently diagnosed and fixed the same deletion (PRs #192 / #193 / #195), two of which became duplicates on rebase.

  New `lib/managed-region.sh` puts the boundary inside the file. `task-init` writes the rendered template between `<!-- task-init:managed:start -->` and `<!-- task-init:managed:end -->`, followed by an empty `## Repo-specific notes` tail. A `--force` (or TTY-overwrite) re-run rebuilds only the region and copies everything outside it verbatim, so the refresh is non-destructive by construction and no longer prompts about the workflow doc at all. `--restore` and the non-TTY `keep` default are unchanged — they still leave an existing doc entirely alone. A doc predating the markers has no boundary to read, so `task-init` adopts it: one that is byte-identical to the template is re-wrapped silently, and a customized one is copied to `<doc>.bak` before the markers go in, with a stderr note telling you to move what you want to keep below the end marker. Nothing is ever deleted. All seven loadouts share the lib (drift-guarded by a new `managed-region-source` sentinel), and this repo's own `.claude/gh-workflow.md` now carries the markers with its checklist below the end marker — so the file that was clobbered three times is the fixture proving the fix.

  **Upgrading: re-run `task-init <loadout>`** to convert an existing workflow doc to the managed-region layout. That first re-run is the adopting one — look for a `<doc>.bak` beside it, move any repo-specific sections below the `<!-- task-init:managed:end -->` marker, then delete the backup. Every re-run after that preserves them in place automatically.

- **#182's cross-repo adoption filter never once executed and failed open, so the first `pm-<repo>` to boot anywhere adopted every other repo's backlog — adoption now routes on `from:`, the field every message actually carries.** `_adopt_legacy_pm_inbox` decided ownership from a message's `repo:` frontmatter field, which `cmd_send` writes **only** when `--repo` is passed. Nothing passes it: 0 of the 163 `radio send` call sites across every prompt and doc, and 0 of the 399 real messages in the mailbox that filed this. So the filter's inner branch had never run in production — and its untagged fall-through *adopts*, on the reasoning that "a repo-less message is a genuinely global backlog entry, so first-come is correct." That made a guard which never ran indistinguishable from one that ran and said yes. **The one signal that would have exposed it could not fire either**: `skipped` was incremented only inside the dead branch, so the `left N foreign-repo message(s) for their own PM` log line was structurally unreachable. Observed 2026-09-14: this repo's PM registered and migrated **53 messages belonging to four other repos** out of `mailbox/pm/` and into its own inbox, stamped `adopted-from:`, with no warning and no log line — one of them live, an open PR with an unaddressed reviewer finding. A PM for those repos booting later would have found nothing, because the mail was gone from where it would look. The general shape is worth naming: **a precondition that is never satisfied turns a guard into a no-op, and a no-op that fails open looks exactly like correct behaviour** — #206 was the same class from a different angle, a drift-shared region reading an `$AUTO_MODE` its three kiro hosts could never set. The fix routes on `from:`, which every message carries and which encodes the repo by construction (`worker-<reponame>-<slug>`, `reviewer-<reponame>-pr<N>`, `pm-<reponame>`). **Direction is what makes the sender the right field**: adoption candidates are worker→pm mail, so they are all literally `to: pm` and the recipient carries no information — the mirror of #201's dead-letter routing, where the sender is also the signal because that mail is PM→worker and the PM that sent a ping is who needs the report. The test is one-sided — adopt iff `from` matches `worker-<my-repo>-*` / `reviewer-<my-repo>-*` / `pm-<my-repo>` — so only one candidate name is ever compared and the hyphen-splitting ambiguity `_resolve_pm_by_slug_split` has to rank around never arises. A repo-scoped sender naming a *different* repo is now left in `mailbox/pm/inbox` for its own PM, and the `left N foreign-repo message(s)` line fires for real. A message no name can attribute (`from: unknown`, from before the role env existed) keeps the historical first-come treatment — it is the only available option — but is counted and logged as such, so "adopted because unattributable" stops being indistinguishable from "adopted because it matched". `repo:` is kept as the **higher-precedence** arm for the day something starts passing `--repo`; per the ticket this does **not** change `cmd_send` to begin writing it, which would be a wire-format change affecting every sender for no benefit `from:` doesn't already provide. Everything else about adoption is unchanged: the `pm-*`-only and live-literal-`pm` guards, the fresh-register gate, the single-winner lock and its stale-lock reclaim, collision-safe migration, the `adopted-from:` provenance header, and the ordering that runs adoption **before** gc's piggyback (#201 added a second reason to respect it — `pm` is exempt from dead-lettering specifically so the backlog isn't archived before adoption can route it). **The test requirement is the point of the ticket, not boilerplate**: the four existing filter tests each fabricate a `repo:` field via `--repo`, so they pinned a branch production cannot reach and passed for months while the feature was inert. Twelve new tests build every fixture the way `cmd_send` really does — no hand-injected `repo:` — and were confirmed to fail against the unfixed binary; the old four are kept, relabelled as what they are, to cover the higher-precedence arm. This is the same discipline #205 landed for `$TASK_FORCE_HOME` and #208 for the `radio-env-injection` precondition: make the harness unable to lie about the thing it is checking. **No recovery migration**: the 53 already-misadopted messages retain their `from:` and could be re-routed, but all 53 are acked and their PRs merged, so a one-shot re-route would move dead mail between mailboxes for no reader — decided explicitly rather than by omission. *Upgrading: re-run `task-init <loadout>` in each configured repo to pick up the revised adoption paragraph; no migration needed, and nothing in the mailbox changes until the next fresh `pm-<repo>` register.* (#210)

- **Mail addressed to a role that has exited is no longer immortal — `radio gc` gains a dead-letter stage, so a dead mailbox can finally be reclaimed.** `cmd_gc`'s whole-directory reclaim required `_inbox_empty`, a guard added so the legacy `pm` backlog couldn't be swept out from under #182's adoption. The side effect was that **any** dead role still holding unread mail was protected forever by the very sweep meant to clean it up: 342 messages across 171 dead roles on the machine that filed the ticket, none of which will ever be read, and `radio gc --dry-run` reporting `0 dead mailbox(es)` against all of them. Sampled, the stranded mail is overwhelmingly PM→worker replies that arrived after the worker exited — `approved-and-merged` and `changes-requested` — which makes it **the mechanism behind leaked worktrees**: the worker never received the signal telling it to clean up, so the worktree stayed on disk and the task item stayed un-Done. The leak was never a `task-done` bug; it was undelivered mail. gc now inserts a stage between "undeliverable" and "reclaimed": a role that is dead (no session file **or** a >1h-stale heartbeat) *and* past the cutoff *and* still holding unread mail has that mail moved to `~/.task-force/radio/dead-letter/<role>/` — original filename, id and frontmatter untouched, formalizing the layout of the hand-run 2026-09-14 sweeps — after which the existing whole-dir reclaim proceeds unchanged. It *unblocks* gc rather than working around it. **It is an archive, not a delete**: nothing unread is ever `rm`'d, a move that fails leaves the message in the inbox and drops gc back to the processed-only sweep, and the archive has no TTL of its own (expiring it would be a separate, explicitly-configured decision). Everything the old gate protected still holds — a **live** role's inbox is untouched at any age, a dead role still *inside* the cutoff keeps its mail because it may yet come back, and the literal `pm` role is exempt from **dead-lettering only** so #182's one-time adoption can't be short-circuited (`cmd_register` already runs `_adopt_legacy_pm_inbox` before the gc piggyback for the same reason) — once adoption has drained it, `pm` is an ordinary dead role with an empty inbox and the whole-dir reclaim reaps it as it always could, since exempting the entire role would re-create this ticket's bug for one mailbox (review #1). The count is surfaced where someone can act on it: a fresh PM `register` prints `N message(s) addressed to M role(s) that had already exited were never delivered, and have been archived to …` and consumes the report, so it is injected once rather than on every boot — a PM that learns its merge ping never landed can re-send or clean up manually, where silent immortality taught nobody anything. That report is **routed per PM, not global** (review #2): `$RADIO_HOME` is shared by every repo on the machine, so one sentinel would be eaten by whichever PM booted first — a PM in repo A consuming a report about repo B's roles and B's PM never learning, which is the same cross-repo class as #182's adoption bug. Each message is attributed to its `repo:` field if it has one, else to the `pm-…` that sent it (`repo:` is only written when `--repo` was passed, and none of the documented send commands pass it, so `from:` is the signal that actually fires on the PM→worker mail this is about), else to the dead role itself when *that* was a PM; anything matching none of those lands in an unscoped report any PM may claim, with the role names always listed so a reader can tell whose mail it was. A PM also claims the reports of any `--also` aliases it answers for, since an alias address never fresh-registers on its own. `radio gc --dry-run` reports both the archive and the reclaim it would unblock without performing either, and the summary line now carries a third counter. New log line `gc: dead-lettered role=… msg=…`, cited in the runbook and therefore pinned by `tests/radio_runbook.bats`. This also retires a claim #191's runbook made nine files over: *"there is no dead-letter queue"* was true when written (the #188 spec had wrongly assumed one shipped) and is now false, so the README section — renamed **"Undelivered mail is never deleted"** — and all eight workflow docs are rewritten to name both places to look, `inbox/` for mail still waiting on a live role and `dead-letter/` for mail whose recipient never came back. The guarantee that survives is the one that matters: the message is written to the inbox *before* any wake is attempted, and nothing unread is ever deleted — it just gained a second address. *Upgrading: re-run `task-init <loadout>` in each configured repo to pick up the rewritten runbook section; an already-filled-in workflow doc is yours to edit and is never overwritten without `--force`, so copy the section across by hand if you have customised yours. No migration needed for existing mail — the first `radio gc` after upgrading archives it.* (#201)

- **kiro's `task-work` now parses `--auto`, so a kiro worker can finally be woken without a keypress — the shared auto-submit line had been reading a variable its three kiro hosts could never set.** The `radio-env-injection` region is byte-identical across all seven `task-work` copies and ends with `[[ -n "${AUTO_MODE:-}" ]] && RADIO_ENV_PREFIX+="TASK_FORCE_AUTO_SUBMIT=1 "`. `$AUTO_MODE` is set by the flag loop, which is per-loadout and *outside* the region — and the three `kiro-*/bin/task-work` copies had no `--auto` case, ending their loop at `-*) echo "Error: unknown flag '$1'"`. Two consequences: the injection line was permanently dead on kiro, and `task-work <slug> --auto` — the flag the claude loadouts document and the PM habitually types — **aborted the launch** on a kiro loadout. Because `AUTO_SUBMIT` decides the wake terminator (CR submits, LF types `radio check` into the prompt box and waits for a human Enter), every radio wake to a kiro worker landed unsubmitted; combined with #190 — kiro has no stop-hook drain, no prompt-hook injection and no register-drain, because its hook stdout never reaches the model (#146) — a radio message reached a kiro agent **only if a human pressed Enter in that tab**. kiro's single push path could not self-complete. All three kiro copies now take `--auto`, so the region's line fires and `radio register` persists `AUTO_SUBMIT=1`. Scope is deliberately narrow and documented as such (the `task-pm --auto-submit` precedent, #189): on kiro `--auto` governs **radio auto-submit only** — the permission model is `-a/--trust-all` and stays separate, and the two are pinned orthogonal by tests in both directions. It also threads into `aw_launch_tab`'s `stay_on_caller_tab` exactly as the claude copies already did, so a `--auto` dispatch keeps focus on the PM's tab. Without `--auto`, kiro behaviour is unchanged: LF, human gate. This does **not** buy kiro parity — it makes the one push path able to finish, and adds nothing behind a wake that never lands; the standing `radio check` poll from #190 is still what carries delivery, and the docs say so rather than implying the gap closed. **On the drift check:** `tools/check-drift.sh` verified the region byte-identical and was right to — what it cannot see is whether the region's *preconditions* hold in each host, so a shared block reading a variable the host never defines passes drift and is silently inert. That is a general limitation of the sentinel approach, not an argument against it, and it now has a standing guard: a test asserts every file carrying `# region:radio-env-injection` also carries an `--auto) AUTO_MODE="1"` case in its own flag loop. New `tests/kiro_task_work_auto.bats` (13 tests) covers that invariant plus, per kiro loadout, launch-without-abort, the injected `TASK_FORCE_AUTO_SUBMIT=1`, its absence without the flag, the `--auto` / `--trust-all` orthogonality, `set +H` ordering, and the help text; `tests/zellij_tab_stay_focused.bats` gains the kiro snap-back pair. #191's runbook stated "kiro can never auto-submit" as a permanent limitation across nine doc files — that paragraph is now wrong and is corrected in the same pass: the three kiro steering templates gain the `--auto` flag bullet and a rewritten *`radio check` sitting unsubmitted* row, and the README's `task-work` flag list and *kiro delivery is best-effort* section name the flag alongside the nuance that it adds no backstop. The claude runbook blocks already read correctly and are untouched (both groups stay byte-identical). `tests/radio_runbook.bats`'s assertion that no kiro doc advises `task-work --auto` is inverted rather than deleted, and now pins doc and flag together so advice can never outlive the flag. *Upgrading: re-run `task-init kiro-gh` / `kiro-local` / `kiro-notion` in each configured repo to render the corrected workflow doc into `.kiro/steering/<loadout>-workflow.md` (an already-filled-in doc is yours and is never overwritten without `--force`, so copy the two changed blocks across by hand if you have customised yours). The flag itself needs no re-run — `task-work` installs as a symlink to the shared dispatcher, which runs the loadout copy straight out of the checkout.* Completes #190. (#206)

- **`./run_tests.sh` no longer wipes the live radio session of whoever ran it, 57 times per run.** `tests/task_done.bats` and `tests/task_done_dispatcher.bats` built their `setup()` without any radio-home helper, so `$TASK_FORCE_HOME` was never overridden and `radio`/`task-done` resolved their mailbox root to the developer's real `~/.task-force`. `$TASK_FORCE_ROLE` is inherited from the tab, so the destructive command those suites exercise — `radio unregister --manual`, which wipes a session file unconditionally by design (#198) — landed on the *runner's own session file*: 51 wipes from `task_done.bats` plus 6 from `task_done_dispatcher.bats`, matching the measured full-suite delta of 57 exactly. An agent worker running the suite (which the pre-PR checklist requires) went unaddressable mid-run — `radio send --to <that worker>` answering *"no session … nobody is listening"* while the agent was plainly alive — and the behaviour was initially misdiagnosed as a regression in #187. It also contaminated this subsystem's own failure data: an unknown share of the 3,165 silent wipes the 2026-09-14 audit attributed to `cmd_unregister` were these bursts of exactly 57, repeating one full-suite run apart, which is precisely the log #191's runbook asks people to trust. Isolation is now the default rather than something each file has to remember: a new `tests/setup_suite.bash` runs once per bats invocation and exports a scratch `$TASK_FORCE_HOME` for the whole run, so a suite that forgets the helper degrades to "isolated anyway" — and because bats resolves `setup_suite.bash` from the folder of the first test file, a bare `bats tests/foo.bats` gets it as well as `./run_tests.sh`. Backing that up, `tests/helpers/common.bash` — which every suite loads — now aborts the run with an explanation if `$TASK_FORCE_HOME` is unset or points at the real `~/.task-force` (skipped only on bats' pre-`setup_suite` test-gathering pass, where an unset value proves nothing). Both suites also got the per-test `setup_task_force_home` they were missing, and `teardown_all` now removes `$TASK_FORCE_HOME` only when the test created it, so a per-test teardown can't delete the run-scoped one. New `tests/radio_home_isolation.bats` is the standing guard: it drives real bats child-runs of both suites under a throwaway `$HOME` and asserts nothing appears under `$HOME/.task-force` — `sessions/`, `mailbox/` and `log` together, with the log pre-created so the check is "nothing was appended", not just "nothing was created" — plus that a subverted `$TASK_FORCE_HOME` fails loudly instead of writing to the live mailbox. Verified: full 1,000-test suite, `./run_tests.sh task_done` and `./run_tests.sh task_done_dispatcher` all now produce delta 0 against `grep -c 'unregister role=' ~/.task-force/radio/log`. Tests only — **no `task-init` re-run needed**, no installed artifact changed. (#203)

- **The Stop hook no longer strands a message that arrives during the drain turn — the loop-breaker compares the unread id set, not the `stop_hook_active` flag.** `cmd_stop_hook` blocks the stop when the inbox is non-empty so the agent drains it (#163), and guarded against an infinite continuation by allowing any `Stop` whose payload carried `stop_hook_active: true`. That test is a boolean, not an inbox: a message queued *during* the forced-continuation turn (the agent is `busy`, so `cmd_send` queues with no wake) hit the same "already had your continuation" branch and the role went idle with unread mail in its own mailbox. For an idle `--auto` worker awaiting `approved-and-merged` that is terminal — no human prompts it, so #164's prompt-hook injection never fires, and no `SessionStart` follows, so #168's drain-on-register never fires either. Draining the pre-existing literal-`pm` backlog post-migration is a tracked follow-up. **Upgrading**: re-run `task-init <loadout>` in each configured repo to refresh the `/planner` / `/worker` / `/reviewer` prompts in `.claude/commands/` — *recommended, not required*: the wire format (`--to pm`) is unchanged from pre-#165, the shim resolves it correctly, and `radio` / `task-pm` / `task-work` are shared symlinks from root `bin/` (no hook or settings change). (#165)
- **The `/worker` prompt now carries a pre-PR checklist — the recurring review findings from the radio bundle are caught before review, not during it.** Four consecutive radio PRs (#172–#175) drew the same review classes: a missing or incomplete CHANGELOG entry (3 of 4), a missing README/steering doc beat for a behavior change (3 of 4), re-implementing a helper the codebase already had (2 of 4), and skipping instructions left as comments on the spec issue (1 of 4). Each claude `commands/worker.md` (gh / jira / notion / local, plus this repo's dogfooded `.claude/commands/worker.md`) gains a five-item checklist between the commit step and PR creation, to walk before radioing `review-requested`: add a changelog entry if the repo keeps one, a docs beat for user-visible changes, a reuse grep before writing scaffolding, a re-read of the spec in full (including comments/notes added after the body), and a green-suite + linters + consistency-checks + `gh pr checks` gate. The checklist is deliberately **repo-generic** — `worker.md` ships downstream verbatim via `task-init`, so it names no file that only exists here and cites no bare issue numbers (which would resolve to a downstream repo's own PRs); this repo's specifics (`./run_tests.sh` + `tools/check-drift.sh` + `shellcheck -x`, the keepachangelog + `task-init` Upgrading convention, the `steering/*.example.md` doc beat, the #163/#164/#168 precedent) live in `.claude/gh-workflow.md`, the per-repo file `task-init` already templates. The checklist block is byte-identical across gh / jira / notion (and the `.claude` dogfood copy); claude-local adapts the spec item to its comment-less `tasks/NNN-slug.md` files. A `tests/worker_checklist.bats` guard enforces the dogfood parity and the repo-generic invariant (no task-force-only paths, no bare `#N`). Kiro worker agents are a deliberate follow-up, tracked in #178. **Upgrading**: re-run `task-init <loadout>` in each configured repo to pull the updated `/worker` prompt into `.claude/commands/`; without it the repo keeps the old prompt. (#176)
- **`task-work --auto` spawns the worker tab without stealing focus from the caller.** Zellij's `new-tab` has no `--no-focus` flag, so dispatching a worker from PM always snapped focus into the new tab — friction when running 3–4 parallel `--auto` workers back-to-back. `aw_launch_tab` now takes an optional `stay_on_caller_tab` arg; `--auto` task-work threads `$AUTO_MODE` through so the launcher captures the caller's tab position via `zellij action list-tabs --json` before `new-tab`, then snaps focus back with `go-to-tab <pos+1>` after. Default `task-work` and `task-work --plan` are unchanged — both still land in the new tab (planner is interactive; you want to be there). Defensive: all gates (`$ZELLIJ` unset, `jq` missing, empty position, non-zero `go-to-tab`) fall through to the legacy focus-shift path; the worker spawn never aborts because the snap-back failed. (#130)
- **Opt-in auto-submit on radio wake-up for `--auto` workers.** `radio send`'s zellij `write-chars` wake-up has always written `radio check\n` (LF) into the recipient's pane, leaving it sitting in the input box until the user pressed Enter. For workers launched via `task-work --auto` — already an explicit autonomy opt-in, and idle most of their life waiting on PM — that human gate is friction with no upside. `task-work --auto` now exports `TASK_FORCE_AUTO_SUBMIT=1`; `radio register` / `_ensure_session_file` persist that as `AUTO_SUBMIT=1` in the session file; `cmd_send` reads it and switches the wake-up byte to CR (`\r`), which Claude Code's raw-mode input binds to Enter. PM and default (non-`--auto`) workers leave the flag unset and keep the LF wake-up, so a `radio check` ping can never corrupt a partially-typed prompt. (#128)

## [0.2.2] — 2026-05-23

Patch release. Extends the cross-tab targeting fix from `v0.2.1` (radio) to `task-done`, and hardens the radio session lifecycle so intra-session Claude events (`/clear`, `/compact`, resume) don't brick subsequent radio operations.

### Fixed

- **`task-done` close-tab no longer targets the focused tab.** The final `zellij action close-tab` in `*/bin/task-done` had no explicit tab id, so if the user switched focus to another tab (e.g., PM) while a worker was auto-cleaning up, the wrong tab got closed — destroying the user's active session. Same root cause as #102, in a different binary. `task-done` now captures the worker's stable `TAB_ID=` from its radio session file *before* `radio unregister` runs, and closes the tab via `zellij action close-tab-by-id`. If no tab id can be captured (zellij not running, no role, missing session file), close-tab is skipped — never falls back to the unscoped call. (#107, #108)
- **Radio session file survives intra-session Claude events.** Claude Code's `SessionEnd` hook fires on `/clear`, `/compact`, and session resume in addition to real exit. The old `radio unregister` hook proceeded unconditionally, wiping the session file mid-life — observed in production as bursts of 40+ unregister calls within ~25s, with subsequent `busy`/`ready`/`send` operations logging "no session file" for the now-missing role. `cmd_unregister` now reads the JSON payload piped by the hook and skips when `reason` is `clear` or `resume`; manual `radio unregister` (no stdin payload) still works. Companion `_ensure_session_file` in `_update_state` self-heals if a stale unregister did get through. (#108)

### Internal

- New bats coverage: `tests/radio_lifecycle.bats` and `tests/task_done_close_tab.bats` pin the contract for both fixes.

## [0.2.1] — 2026-05-22

Radio polish + reliability patch. Lifecycle / UX fixes building on the `v0.2.0` radio rollout, plus a tab-targeting fix that hardens cross-tab routing.

### Fixed

- **Radio hooks no-op when `$TASK_FORCE_ROLE` is unset.** Plain `claude` in a task-force-equipped repo was getting blocked at every prompt because the `UserPromptSubmit` hook (and friends) erred out when no role was set. Hook-invoked subcommands (`busy`, `ready`, `check`, `unregister`, `register --role ""`) now silently exit 0 when role is missing; user-invoked subcommands (`read`, `ack`) still fail loudly. (#93, #96)
- **Auto-unregister radio sessions on session/worker end.** Worker session files were orphaning in `~/.task-force/radio/sessions/` after a worker finished. Two new lifecycle beats: a Claude `SessionEnd` hook calls `radio unregister`; `task-done` calls `radio unregister` before tearing down the worktree. (#94, #97)
- **Radio tab/pane actions no longer target the focused tab.** Both `_rename_tab` (idle/busy emoji prefix) and `radio send` (wake-up via `radio check`) used `zellij action` calls without explicit tab targeting, so they clobbered whichever tab the user happened to be focused on — e.g. PM's tab name got rewritten when a worker auto-unregistered, and `radio send --to pm` from worker B mis-delivered the wake-up to worker A. Now both paths drive zellij via stable tab/pane ids captured at `radio register` time (`TAB_ID=` in the session file), with `rename-tab-by-id` and `write-chars --pane-id`. Routing is name-collision-proof and survives user-driven `rename-tab`. (#102, #103)

### Added

- **Idle/busy emoji in zellij tab names.** `radio` now prefixes the current tab with `⏸️` (idle) or `▶️` (busy) so you can see at a glance which workers are mid-turn vs. waiting on input — useful when running several workers in parallel. `TAB=` in the session file is kept in sync so `radio send`'s `go-to-tab-name` wake-up still finds the renamed tab. (#95, #99)

## [0.2.0] — 2026-05-21

Headline: **PM ↔ worker radio messaging.** A persistent mailbox CLI plus a canonical 5-row handoff protocol baked into every role's prompt. Workers now defer `Status=Done` and worktree cleanup until the PM signals `approved-and-merged`, so the whole spec → review → merge loop runs through `radio send`.

### Added

- **PM ↔ worker messaging (radio):** new `radio` mailbox CLI (`send` / `check` / `read` / `ack` / `register` / `ready` / `busy` / `unregister` / `orphans`) plus `task-pm` for in-place PM-tab takeover. Hook-driven session registration is auto-installed by every `task-init` (claude-\* via `.claude/settings.json` jq merge, kiro-\* via `.kiro/hooks/`). Idle recipients are woken via `zellij action go-to-tab-name`; busy recipients queue-and-defer. (#63)
- **Canonical radio handoff protocol** baked into every role's prompt — 5 transitions: `spec-ready`, `review-requested`, `re-review-requested`, `changes-requested`, `approved-and-merged`. Worker now delays `Status=Done` and `task-done --remove-worktree` until PM signals `approved-and-merged`. (#75, #82)
- **`task-init` seeds `Bash(radio *)`** into `.claude/settings.json` `permissions.allow` across all claude loadouts so radio calls don't trigger permission prompts. (#83)
- **`task-init --restore`:** fill in only the files that are missing; never touch anything that already exists. Lets you restore a deleted slash command / agent without re-typing your board IDs. (#37)
- **`task-init --workflow` / `--commands`:** scope the run to just the workflow doc, or just the slash commands / agents. Compose with `--force` / `--restore` for surgical refreshes. (#37)
- **Per-file `[k]eep / [o]verwrite / [d]iff` prompt:** in a TTY, when a target already exists `task-init` prompts per file (default = keep). Old behavior was hard-fail with "Use --force." (#37)
- **Placeholder preservation:** when re-rendering the workflow doc, previously-filled `{OWNER}` / `{REPO}` / `{PROJECT}` / `{SITE}` / `{KEY}` / `{BOARD}` values are carried forward automatically. Precedence: this-run flag → existing-file value → leave the `{PLACEHOLDER}` token. (#37)
- **Shared helpers:** `lib/install-file.sh` (exists / prompt / diff / overwrite / keep decision) and `lib/preserve-placeholders.sh` (generic placeholder extractor), with unit tests in `tests/install_file.bats` and `tests/preserve_placeholders.bats`. (#37)

### Changed

- **`claude-gh` / `kiro-gh` now standardize on the `gh` CLI** for issue and project reads (previously: GitHub MCP). `task-init claude-gh` seeds a read-only `gh` allow-list into `.claude/settings.json` (`gh issue view *`, `gh project view *`, `gh search issues *`, etc.) so the PM / planner / worker can read freely; mutations stay confirmation-gated. The GitHub MCP is documented as an **optional** add-on for users who frequently mutate Projects v2 fields. (#69)

Mutations across all loadouts remain confirmation-gated. (#69)
- **`task-init` no longer hard-fails when target files exist.** In a TTY it now prompts per file (`[k]eep / [o]verwrite / [d]iff`, default = keep). In a non-TTY context it silently skips existing files and exits 0. `--force` (unchanged behavior) remains for unconditional overwrite. (#37)

### Fixed

- Installer prompts: arrow keys (↑/↓/←/→) now provide readline navigation instead of echoing raw escape sequences (`^[[A`). Switched `read -rp` → `read -erp` in `install.sh`, `task-init`, and `*/bin/task-init`. (#23)
- **task-init:** silenced ShellCheck SC2016 false-positive on the `_preserve_placeholders` regex backticks. `main` had been red on this check since #37. (#71)
