### Changed
- **`task-work` is one canonical script composing a tracker module and an agent module; the seven per-loadout copies are gone (#237, epic #122 Phase 2).** Seven `<loadout>/bin/task-work` files, 2124 lines, whose variation ran along two orthogonal axes rather than seven shapes. The **tracker** (`lib/trackers/<tracker>.sh`, over `_default.sh`) now decides ref parsing, the slug a ref derives, the usage synopsis, the `.info` key and the worker-prompt payload, plus `local`'s `state.json` write and board regen — 16 lines that were byte-identical between the two local copies with no drift sentinel on them. The **agent** (`lib/agents/<agent>.sh`) decides the extra flags, kiro's #218 preflight, the launch line and the completion message. Everything else is the one shared body in `bin/task-work`. The agent module gets first refusal on every command-line token — a `case` arm cannot be injected by a function call, and kiro's `-m` / `-a` used to sit interleaved in the shared `case` — and `tests/task_work_agents.bats` pins that no agent module claims a shared flag. `--auto`'s effect on the radio auto-submit prefix stays the body's on every agent; only claude's launch line also reads it, as `--permission-mode auto`. All ten `task-work*` drift groups are retired (15 groups, was 25). Declared behaviour changes:
  - **`claude-jira` catches up with the other six.** It gains `--no-launch`, the `--` passthrough, the `<slug> <ref>` form, the `could not derive a slug from input` guard and the standard `Started worker in …` wording (was `Worker started in …`); `--help` now exits **0** (was 1), and `not in a git repo` goes to stderr.
  - **`claude-jira` error precedence.** With both an underivable slug and a non-repo `$PWD`, it now reports the slug error first, as the other six always did.
  - **`claude-local`'s worker prompt is `/worker Implement task: <file>`** (was `/worker <file>`). `kiro-local` already sent `Implement task: <file>` — same tracker, different text. The payload is the tracker's now and only the wrapper is the agent's, so the two locals agree.
  - **`kiro-notion`'s `--help` example URL is fixed.** It showed a 12-hex page id, which the 32-hex slug rule never matches.
  - **`--help` is composed** from both axes, so option order shifted: kiro's `-m` / `-a` now follow `--no-launch` instead of leading, and claude's `--plan` sits beside `--auto`. Tokens and texts are otherwise unchanged.
  - Board regen already named `bin/task-work` as its caller since #238, so `aw_regenerate_board`'s sibling fallback resolves exactly as before.
  
  Tests: the eight per-loadout `task-work` suites plus `claude_task_work_auto_submit.bats` (219 tests at `1f66c20`) become `tests/task_work.bats` (the shared body, run once as `claude-gh`), `task_work_trackers.bats`, `task_work_agents.bats` and a per-impl table, `task_work_impls.bats`, whose rows are derived from `aw_all_impls` and each assert an observable a failed module load cannot produce. `tests/loadout_modules.bats` gains the task-work hook lists and proves that deleting any tracker or agent module makes `task-work` fail cleanly before creating anything. No `task-init` re-run needed: every installer already links `~/.local/bin/task-work` to the root `bin/task-work`, and no installer-written artifact changed.

- **`task-board` is one canonical script; the two byte-identical per-loadout copies are gone (#238, #122 Phase-1 residue).** `claude-local/bin/task-board` and `kiro-local/bin/task-board` were 175 lines each with a `diff` of nothing, held in step by a `task-board|board-render` drift group — the evidence #170 used to consolidate `radio` / `task-pm` / `task-reviewer`, which this one missed. The render body now lives in `bin/task-board` below the loadout check it already carried: `--repo PATH` detection and the #215 refusal on gh/jira/notion are unchanged, and the rendered `tasks/_board.md` is byte-identical to before on both local loadouts. The drift group is retired (25 groups, was 26). The sibling fallback `lib/board-regen.sh` uses when `$PATH` has no `task-board` used to find the copy beside `<impl>/bin/task-work`; there is none there now, so the two local `task-work`s and `lib/trackers/local.sh` name the root `bin/task-work` / `bin/task-done` as the caller, and the fallback lands on `bin/task-board` — pinned by a new `tests/board_regen.bats` case. One consequence: the fallback copy now detects the loadout before rendering, as `$PATH`'s copy always did, so a repo with no local workflow doc gets a warning instead of a board. No `task-init` re-run needed — every installer already links `~/.local/bin/task-board` at `bin/task-board` (#215); `install.sh` only relabels it `(canonical)`.

- **`task-done` was a three-variant file wearing seven copies; it is now one canonical script composing one tracker module (#236, epic #122 Phase 2).** `md5` told the whole story: `claude-gh`, `claude-notion`, `kiro-gh` and `kiro-notion` were byte-identical; `claude-local` and `kiro-local` were byte-identical to each other; `claude-jira` differed by **seven lines**. 1525 lines expressing about 249 distinct ones — roughly 96% of every `task-done` byte in the repo was duplication, held in step by ten of the 35 groups in `tools/check-drift.sh`.

  **The part that genuinely differed was the part with no sentinel on it.** The `gh pr view` / `gh pr create` block (`claude-gh/bin/task-done:87-97`) is the only tracker-specific code in the file, and it sat *between* two drift-guarded regions while being guarded by neither. Jira's uppercasing of a Jira-key slug for `--title` could have been fixed, or broken, in one copy and nothing would have said so. Meanwhile the local loadouts' `board-regen` region was *nested inside* `confirm-and-cleanup`, and `extract_region` (`tools/check-drift.sh:52`) is a plain awk window — so the outer extract swallowed the inner sentinels and body, and passed only because both local copies happened to be identical.

  **There is no agent axis here at all, and that is the finding that shaped the design.** `diff claude-gh/bin/task-done kiro-gh/bin/task-done` was empty; neither copy ever mentioned `claude` or `kiro-cli`. Removing a worktree, sweeping radio state and closing a tab does not depend on which agent was sitting in the tab. So a loadout is `{tracker × agent}` and the modules are keyed on the **axes**, not the combo: `lib/trackers/{gh,jira,notion,local}.sh` and `lib/agents/{claude,kiro}.sh`, four files and two, not seven of each. `#122`'s body says "per-loadout `hooks.sh`" in one place and "{tracker module × agent module}: 4 + 2 small files" in another; the second is right, and the first would have kept the file count *and* kept the gh verbs duplicated between `claude-gh` and `kiro-gh`. `kiro-jira` (#92) now reuses `jira.sh × kiro.sh` with **zero new module files** for this tool.

  Three hooks carry it, and four of the seven loadouts override none of them: `aw_tracker_pr_section` (jira overrides), `aw_tracker_usage_steps` and `aw_tracker_post_cleanup` (local overrides). `lib/trackers/_default.sh` holds the behaviour the four byte-identical copies actually had, so `gh.sh` and `notion.sh` override nothing rather than restating an identical PR section — otherwise seven copies would merely have become four. `aw_tracker_module` / `aw_agent_module` live in `lib/detect-impl.sh` beside `aw_all_impls`, which #219 established as the single home for "which loadouts exist"; `aw_all_trackers` / `aw_all_agents` derive the axis names from that list rather than restating them.

  **No behaviour changes. Not one.** Every message, exit code and code path is preserved, jira's uppercasing and local's five-step usage text included — which is what made this the right half of Phase 2 to land first, and a cheap proving ground for the module loader. One candidate change was designed out rather than accepted: `aw_regenerate_board` defaults its `self` to `${BASH_SOURCE[1]}` (`lib/board-regen.sh:30`), which from a tracker module would have resolved to a file with no `task-board` beside it, silently finding nothing through the sibling fallback. The two local board tests caught it immediately; `aw_tracker_post_cleanup` now takes the impl and names that loadout's own `task-done`, so `$PATH`-first-then-sibling resolution stays byte-identical to before. #238 consolidates the two `task-board` copies and moves that line with it.

  **The test count went from 1397 to 1379, and here is why that is not a coverage loss.** The port was done in two steps on purpose: first retarget all 67 `task_done` cases at the canonical script with `AW_IMPL` and confirm the suite green with the duplication still present — proving the port behaviour-preserving — and only then retire it. 32 of those 67 asserted shared-body behaviour two or three times over, once per loadout; each was removed only where an identical assertion survives, and the PR body lists every one by name against its counterpart. What was *kept* is the part that means something: the two jira PR-title cases, the two local board cases, and the seven-row `unregisters the radio session` table — the only place all seven impls run the full script end to end, which is what would catch a module that loads but never fires.

  **On the number itself, since this entry makes it load-bearing:** it is `bats --count`, not `grep -c '^@test'`. The two disagree by one — `tests/radio_home_isolation.bats:105` has an `@test` line inside a heredoc that writes a generated `probe.bats` fixture, so grep counts a test bats never runs. An earlier draft of this entry quoted the grep figures (1381 → 1361) while the PR body quoted the measured ones; the nets agreed at −20 either way, but two different baselines in the repo's two durable records undercuts exactly the credibility the retirement table is for. The measured count is the one to quote. The arithmetic, so it can be checked rather than believed: 1397 baseline − 32 retired + 14 added = 1379, and `bats --count tests/*.bats` returns 1379. The baseline is `origin/main` *after* #243, which added 17 of its own; an earlier draft quoted 1380, the pre-#243 figure, which is why this entry names the ref as well as the tool.

  That last distinction is #206's lesson restated: a region can be byte-identical and still inert when a precondition differs. Structural parity cannot see it. So `tests/loadout_modules.bats` (14 new cases) proves every module **loads** — derived from `aw_all_impls`, never a second copy of the list, failing on a **missing** file, on an **orphan** file, and on a module that loads but forgot a hook — and `tests/task_done.bats` proves the right one **ran**. Both halves were demonstrated to fail, not assumed to: deleting `lib/trackers/notion.sh` fails 4 parity cases and 37 behavioural ones, and adding a stray `lib/trackers/linear.sh` fails the orphan assertion. That demonstration is the floor that makes a falling test count trustworthy; a retirement rule without it is an honour system.

  **Review follow-up, and it was not the nit it looked like.** The composition call site was `source "$(aw_tracker_module …)" || exit 1`, which reads as resolve-then-source and is not: on a missing module the helper writes its diagnosis and exits 1, but the command substitution has already yielded the empty string, so `source ""` runs and bash appends `: No such file or directory` naming a line in `task-done` before `|| exit 1` is reached. It is now two lines, resolving before sourcing.

  The part worth recording is why the existing test did not catch it. `aw_tracker_module names the missing file rather than letting source fail` passed either way, because it exercised the helper **directly and never went through the call site** — a name promising more than it checked, so a green suite would have told the next reader something untrue. That is the same shape as the misnamed table row this PR caught in its own test rename. Both helper tests are renamed to say they test the helper, and two new cases run the real `bin/task-done` against a checkout with a module removed and refute the shell noise — one for `gh`, one sweeping all four trackers. Both were verified to fail against the old call site before landing, which the first draft of them did not: they asserted `source: : not found`, the message the review described, rather than the one bash actually emits.

  **Rebased onto #243, carrying its change forward rather than resolving by deletion.** #243 (#242) landed first and touched all seven `bin/task-done` copies — the files this deletes — so a rebase that took either side whole would have lost a P0's work or this one's. Four things came across: the `_TAB_ID_MISS` block and the second skip line, which name *which* source came up empty and print the `grep 'tab-id:'` that finds the launch-time log line, now in the canonical body where seven copies of it became one; both README edits; both CHANGELOG entries; and #243's three `task-done` cases in `tests/tab_id_capture.bats`, retargeted from `$CLAUDE_GH_TASK_DONE` to the canonical script with `AW_IMPL`. **Their assertions are unchanged and they pass against this shape**, which is the evidence the port is faithful rather than merely plausible. #243's nine runbook docs (7 templates + README + this repo's own `.claude/gh-workflow.md`) are untouched.

### Fixed

- **`task-recreate-worker` relaunched every non-gh worker with no task (#240).** It read the task ref from the `.<slug>.info` sidecar under `GH_URL` on every loadout, but each tracker's `task-work` writes its own key — `NOTION_URL`, `JIRA_REF`, `TASK_FILE` (the spec's table said `SLUG` for local; the module says `TASK_FILE`). So on five of the seven loadouts the report said `none recorded` and the rebuilt agent came up as a bare `/worker` with no idea what it was working on, which is most of the way back to the hand-rolled tab the command replaced. Nothing was lost on disk: the sidecar rewrite preserved the key, it was just never read. It now sources the tracker module and reads `aw_tracker_info_key()` (#237), and builds the relaunch payload with `aw_tracker_worker_prompt`, so `claude-jira` gets `Implement Jira issue: <key>` exactly as `task-work` launched it. The rewritten sidecar keeps the ref under the tracker's key instead of adding an empty `GH_URL=`. A sidecar with nothing under that key now names the key it looked for — `none recorded (NOTION_URL is empty or absent in .<slug>.info)` — and a stray `GH_URL` on a non-gh sidecar is deliberately not picked up. `claude-gh` / `kiro-gh` output is unchanged. The rest of the command's inline agent/tracker switches move onto the modules in #239. No `task-init` re-run needed: `~/.local/bin/task-recreate-worker` already links the canonical script.

- **A missed tab-id capture was silent at launch and surfaced hours later as `task-done`'s "no tab id captured" (#242).** `task-work` appended `TAB_ID=` to the `.<slug>.info` sidecar on a hit and did nothing on a miss — no message, no log line, not even a `$ZELLIJ` check — so the only symptom was a teardown message reporting a *consequence*, in a different command, after the context that explained it was gone. Same failure shape as #194, #182 and #229: a state invisible because its failure produces no artifact.

  **The capture is now loud, logged and still non-fatal.** A new `aw_record_tab_id` in `lib/zellij-tab.sh` replaces the silent block in all seven `task-work` copies (the drift-guarded `info-tab-id` region) and in `task-reviewer` (both copies) and `task-recreate-worker`, which carried the same three lines. On a miss it prints to stderr why, and names the slug it searched for, and appends a `tab-id: <caller> capture missed slug=… reason=… info=… detail=…` line to `~/.task-force/radio/log`. The reasons it can tell apart: `no-zellij-bin`, `not-in-zellij` (`$ZELLIJ` unset), `no-jq`, `list-tabs-empty`, `race` (the tab is listed by the time the diagnosis re-queries), and `no-match`, which carries the slug's length and every tab name zellij reported, JSON-quoted, so a byte-level mismatch shows up in the line itself. A hit prints nothing, so successful output is unchanged; a miss still lets the worker launch.

  **`task-done` links the two ends.** Its "Skipping zellij close-tab (no tab id captured …)" line gains a second line naming which source was empty: `$ZELLIJ` unset, no sidecar at the path it derived from the branch, or a sidecar with no `TAB_ID=` — the last one with the exact `grep 'tab-id:.*slug=<slug> '` that finds the launch-time line. That reason is worked out when the id is read, because the sidecar is deleted before the close step reports it. It still never falls back to the unscoped `close-tab` (#107 / #108).

  **On the trigger: not reproduced, and the issue's evidence has a simpler explanation.** All nine sidecars without `TAB_ID` on this machine have mtimes of 2026-05-12 to 2026-05-14. The capture landed in #118 on 2026-05-24, so they **predate the feature**, and every sidecar written since has its `TAB_ID`. Both suspected shapes were also checked against a real zellij 0.44.2 in a detached session: a 50-character name (`bug-model-renders-table-but-the-chat-already-outpu`), its collision-suffixed 56-character form and `add-readme-7qegu` each came back byte-equal from `list-tabs --json`, matched immediately after `new-tab`. So the intermittent reports must come from some condition those artifacts do not record. The next one now names itself in one line — on either side, since `task-done` can also miss because the branch was switched away from `task/<slug>` or because it ran outside zellij, neither of which is a capture failure.

  Upgrading: no `task-init` re-run needed — the change is in the shared `lib/` and `bin/` scripts that the `~/.local/bin` symlinks already point at. The runbook row is new in the workflow templates; re-run `task-init <loadout>` only if you want it in an installed workflow doc.

- **Agent-authored prose was being interpolated into a double-quoted shell string, so every backticked token in a review was command-substituted before it reached GitHub (#234).** The `/reviewer` prompt said, literally, `gh pr comment <N> -b "<full analysis>"`. The agent followed it, built a double-quoted string containing its own prose, and the shell got there first. On PR #233's review, `` `pwd -P` `` posted as the reviewer's working directory and `` `radio orphans` `` posted as that command's tab-separated output, complete with an unrelated live role's heartbeat. `bin/task-reviewer` was never the culprit — the instruction it spawns an agent to follow was.

  **The silent half is the one that matters.** A backticked identifier that names no command substitutes to *nothing*: `` `$WORKTREE_DIR` ``, `` `_resume_session_id()` `` and others vanished outright, so findings lost their subjects and the review read as if words were missing, with nothing to signal that anything had been removed. A noisy corruption you can see; a deletion you cannot. And the reviewer is single-shot and self-destructing by design (#138 / #162) — its tab is gone and the PR comment is the only surviving artifact — so a mangled comment is an unrecoverable loss of the analysis, in a repo that routinely re-reads reviews with `gh pr view <N> --comments`. It is also arbitrary execution driven by prose: every backticked token in a review runs in the reviewer's worktree, and review prose quotes `rm`, `git reset` and `gh pr merge` while discussing a diff.

  **The fix is `--body-file -` off a quote-delimited heredoc**, in all 30 shipped prompts — 20 markdown (4 claude loadouts × {pm, planner, worker, reviewer}, plus this repo's own four in `.claude/commands/`) and 10 kiro agent JSONs. `gh` takes `--body-file -`, `radio send` takes its body on stdin whenever `--body` is omitted, and `git commit` takes `-F -`; all three read a `<<'BODY'` heredoc, whose **quoted delimiter** is the part that does the work — an unquoted `<<BODY` substitutes exactly as `"…"` does, and a test pins that distinction. Single-quoting `-b '…'` is explicitly *not* the fix: review prose reliably contains apostrophes, and the first `don't` ends the string, leaving the rest to be read as shell.

  **The trap, stated so the next person does not fall in it:** `grep -rn -- '-b "'` finds the 20 markdown prompts and **misses all 10 kiro agent JSONs**, because inside a JSON string the quotes are backslash-escaped (`-b \"`). Fix this by grep alone and you ship 20 of 30 files fixed with kiro silently still broken — the same 6-of-7 doc-parity failure `tools/check-drift.sh` exists for. So `tests/prose_body_file.bats` reads each prompt through one accessor that unwraps the JSON, asserts the sweep resolved to exactly 30 real files before trusting any negative assertion over them, and only then checks that no prompt hands `gh`, `radio` or `git commit` a body in double quotes.

  **Scope beyond the reviewer, since the defect is the shape and not the site.** PM composes review comments, issue bodies and multi-paragraph merge notes; the gh planner writes a backtick-dense spec into an issue body; and the worker writes commit messages, where this repo's bodies name files and symbols in backticks by the paragraph and git history is *more* durable than a PR comment. All four roles now carry the rule — 27 of the 30 prompts changed.

  **The boundary is slots, not trackers**, and the first draft of this entry got it wrong in a way worth recording. It reasoned that the five non-gh planners were safe because they write their spec through an MCP call or the `Write` tool, leaving no shell string to interpolate into. That is false for two of them: `claude-notion/commands/planner.md` and `kiro-notion/agents/planner.json` both radioed `--body "spec written for <task name>, ready to dispatch"` — a model-filled slot inside a double-quoted string, on the *ping* rather than the spec write. The rule that actually holds is: **a prompt is safe when every slot in its body is literal, whichever tracker it targets.** The `<task name>` hazard is not hypothetical here — this repo titles its own issues `a resumed session has no $TASK_FORCE_ROLE: …` and `reviewer PR comments are shell-interpolated: backticked code is …`, so a Notion board mirroring this workflow would lose `$TASK_FORCE_ROLE` to an empty expansion in a ticket *about* that variable being unset, and a backticked title would execute. Anchoring the assertion on the start of the body (`--body "<`) missed it because the slot sits mid-sentence; it now matches a `<…>` slot **anywhere** inside a quoted `--body`, which caught the same shape in the worker prompts' `--body "PR up: <url>"` across all 8. Ten bodies in total. The three genuinely literal planner bodies are unchanged, as are the PM's `--body "merged"` / `--body "see PR comments"` — no slot, nothing for the shell to reach.

  Four behavioural tests do the arguing rather than the prose: they would have failed against the old pattern, and they prove the quoted heredoc reaches `gh`, `radio send` and `git commit` verbatim with `` `pwd -P` ``, `` `$SOME_VAR` ``, an apostrophe, `$(…)` and `${…}` all intact.

  **Upgrading:** re-run `task-init <loadout>` — this changes installer-written artifacts (the copied `commands/*.md` and `agents/*.json`) plus the workflow doc's managed region, and an un-refreshed repo keeps instructing its agents to post reviews through a double-quoted string.

- **A resumed session has no `$TASK_FORCE_ROLE`, and every radio beat keyed off it degraded silently — including the one documented as the way out (#229).** `radio check` exited 0 with no output while mail sat in the inbox; `radio send` wrote `from: unknown` into the machine-wide literal-`pm` inbox that #210 makes adoptable first-come by whichever PM boots first, in whichever repo; the role had no session file, so nothing could wake it; and `radio register` — the repair for all three — no-opped, because the dispatcher gated it on the very environment variable it exists to restore, *before* argument parsing, so an explicit `--role` was never read. Observed live after a machine restart: eleven hours and no `register` line, with the handoff relayed by hand.

  **The empirical gate first, because the ticket's own diagnosis was wrong about it.** `SessionStart` does fire on a resume — verified with a canary hook against all four sources (`startup`, `resume`, `compact`, `clear`; project-`settings.json` hooks are not honoured for an unapproved directory, which is why a first attempt appeared to show the opposite). The cause is that a resume is a **new process** while the identity env is a command prefix on the one `task-work` launched — `bash -ic "set +H; TASK_FORCE_ROLE=… ZELLIJ_TAB=… claude …"` — so it lives in no shell and nothing can hand it back. `/compact` and `/clear` keep the same process and genuinely do re-register (the log shows such pairs minutes apart with no `unregister` between). A resume runs the hook with an empty environment, where the *unquoted* `--role $TASK_FORCE_ROLE` in the hook command does not go empty — the argument **vanishes** and `--role` swallows `--tab`, which is also how the historical `--tab` mailbox got created. Both no-op paths now log a line: "the hook never fired" and "the hook fired and register no-opped" left identical (empty) traces, which is the real reason this cost eleven hours of reconstruction rather than a grep.

  **`register` is fixed first, being the precondition for the rest.** Its dispatcher gate now keys on the resolved `--role` argument instead of the env var. That preserves #93 exactly — in a plain `claude` session the value is `--tab`, which fails `_validate_role` for a leading dash just as an empty string fails it, so the hook stays a silent no-op — while an explicit `radio register --role pm-myrepo --tab … --agent claude` typed to un-wedge a session finally runs. A hand-run repair also **reports its own outcome on stderr**, because being told nothing is what hid this: either `registered <role> (tab_id=7, via info-file) — wakeable again`, or a loud warning that `TAB_ID` came out empty. That warning is not cosmetic — an unbound role is strictly worse than an unregistered one, since senders stop getting `WARNING — no session for <role>` and start getting a cheerful `queued` against a role nothing will ever wake — so it names the undo. The hook path keeps #188's legitimate `tab_id_src=none` cases (CI, non-zellij) untouched; the axis is deliberate human repair vs. automatic invocation, the same axis as `check` below.

  **The role is then recovered from disk rather than erroring**, mirroring how #188 recovers `TAB_ID` from the same file. In a worktree, `<worktree-base>/.<slug>.info` (written by `task-work` / `task-reviewer`, never by radio) plus the main repo name rebuild `worker-<reponame>-<slug>` — or `reviewer-<reponame>-pr<N>`, whose tab slug is `review-pr<N>` while its role says `pr<N>`. In a main checkout the repo name gives `pm-<reponame>`, but that candidate is **corroboration-gated** on the role already having radio state on disk (the `.loadout` / `.agent` sidecars that outlive `unregister` by design, or a mailbox): `pm-<reponame>` is derivable in *any* checkout of the repo, and an uncorroborated guess would let a plain `claude` in the repo root claim the PM's address and start acking its mail. No candidate is claimed while its session file carries a **fresh heartbeat** either — only a process holding the role env can write one, so a live heartbeat means another session is that role and this one is not.

  **Recovery stops at identity and does not register.** That is the ticket's own argument, and it holds: a register run from anywhere but the role's own zellij tab misses the tab lookup and writes the empty `TAB_ID` described above, trading a loud failure for a silent one. So a recovered role with no session file is *told* it is unwakeable, with the exact command and where to run it.

  **`check` no longer answers a question nobody asked.** `_silent_exit_if_no_role` stays where #93 put it — `busy` / `ready` / `awaiting` / `stop-hook` / `prompt-hook` / `unregister` are automatic in every plain `claude` session and must stay quiet — but `check` is typed on purpose, and is also what a radio wake types into a recipient's prompt box, so silence there is a wrong answer rather than politeness. Same failure shape as #194's empty check list read as green. It now recovers or fails loudly, and while there it also stops returning early for a role whose mailbox directory does not exist yet: that is an empty inbox, and it should be said in words. `read` and `ack` already failed loudly; they get recovery too, so the inconsistency *within* radio closes as well. A roleless `send` recovers its identity — which also repairs `--to pm` routing, since the shim resolves `pm` through the sender's own role — or refuses, rather than depositing an unattributable report into a shared queue.

  One more silent shape named on the way past: with `$TASK_FORCE_ROLE` set but `$ZELLIJ_TAB` unset, the hook's arguments shift by one and `--tab` takes `--repo` as its value, which surfaced as `register: unknown flag /path/to/repo` — an error naming neither the cause nor the missing variable, and logging nothing. It is now named and logged. `--role` deliberately keeps falling through to `invalid role`: its swallowed shape *is* the plain-`claude` hook invocation, which the dispatcher no-ops before `cmd_register` runs, so the only way to reach it is a human typing a dash-leading role (#169's footgun guard).

  **Upgrading:** the fix itself needs **no re-run** — `radio` runs from the checkout your `~/.local/bin` symlinks already point at, and no hook command changed. Re-run `task-init <loadout>` only to refresh the workflow doc's managed region with the new roleless-session section.

- **Two `regenerates tasks/_board.md` tests failed locally and passed on CI, because the suite was exercising a different checkout's `task-board` (#223).** `task-work` and `task-done` resolve `task-board` from `$PATH` *in preference to* their own sibling copy, and `install.sh` plants `~/.local/bin/task-board` as a symlink into whichever checkout ran the installer last. So on any machine that has ever installed task-force, the board those tests assert on was rendered by **another clone's** code — possibly older, possibly mid-edit — and not by the file under test at all. That copy is `bin/task-board`, the root dispatcher, which resolves its own `AW_ROOT` from its symlink path and then refuses outright on a fixture repo carrying no workflow doc. A `|| true` on the call swallowed the refusal whole, so the failure surfaced two assertions later as a missing artifact with nothing naming the cause. CI installs nothing, takes the sibling-copy fallback, and passed: **the suite was red for exactly the people most likely to run it, and green on the machine that gates merges.** A developer's first encounter with it was two failures unrelated to their change — and by the time this was diagnosed, both had spent a session being waved past as "the known pre-existing failures".

  Same class as the `$TASK_FORCE_HOME` leakage #203 fixed — a test reaching out of its fixture into real machine state — so it gets the same two layers. `tests/setup_suite.bash` rewrites `$PATH` once per run so that none of the ten commands `install.sh` links is reachable by name, and `tests/helpers/common.bash` fails the run loudly if one is anyway. A directory holding one is **mirrored** as symlinks minus our own commands rather than dropped: `~/.local/bin` routinely carries `jq`, `gh` or `python` beside the task-force symlinks, and dropping it wholesale would trade this bug for a worse one. Repeated `$PATH` entries collapse to their first occurrence, so a duplicated directory is mirrored once rather than once per mention.

  **Neutralizing `$PATH` alone would have been the wrong fix, and this is the part worth reading.** With the lookup made to miss, the tests exercise only the fallback branch — which is what CI already covered — and the `$PATH` branch would then be tested by nobody, on any machine. That is precisely the shape the bug grew in: the only thing exercising that branch was an accident of one developer's environment. So both branches are now tested on purpose. `tests/board_regen.bats` pins the resolution order with a stub planted on a controlled `$PATH` and with `$PATH` neutralized, and each local `task-work` suite runs the same pair end-to-end.

  The `|| true` is **not** simply dropped, either. Board rendering is cosmetic; a `task-work` that aborts because the board would not render — after the worktree exists, the branch exists and the tab is open — is worse than one that carries on. So the failure is made loud without being made fatal: a warning on stderr naming which copy of `task-board` ran, passing through that copy's own diagnostics instead of discarding them, and — when the copy came from `$PATH` — saying so and printing this checkout's own copy to run by hand. Under the old code this failure produced no output at all. Reconsidering the `$PATH`-over-sibling precedence itself is a behaviour change across all loadouts with its own blast radius and is deliberately **out of scope** here (#223 direction 3); getting the suite honest first is worth more than getting the precedence philosophically right.

  The four byte-similar copies of the regeneration block — `task-work` and `task-done` on both local loadouts — are extracted to `lib/board-regen.sh` rather than patched four times, per this repo's own reuse rule, with `# region:board-regen` / `# region:board-regen-source` sentinels and `tools/check-drift.sh` manifest entries so the next fix cannot land in three of them. `aw_resolve_task_board` takes the calling script's path as a **required** argument rather than defaulting to `${BASH_SOURCE[1]}`: that default reads as a convenience but could never be right, since every real caller arrives through `aw_regenerate_board`, making `BASH_SOURCE[1]` this library's own frame — and `lib/` has no `task-board` beside it. Documenting a hazard as deliberate is worse than deleting it, so a direct caller that omits it now fails at its own call site.

  Verified in both directions, since a fix that merely inverts which environment fails is no fix: green on a machine **with** `~/.local/bin/task-board` pointing at a different checkout (the condition that reproduces it, and the reproduction is automated in `tests/path_isolation.bats`, which drives real child `bats` runs with a hostile `task-board` first on `$PATH`), and green with nothing installed. **No re-run of `task-init` is needed** — nothing installer-written changed; the touched scripts are used from the checkout your `~/.local/bin` symlinks already point at.

- **`--impl` / `$AW_IMPL` naming a loadout that is not configured in the repo was believed rather than refused, and both commands that take a pin failed by *appearing to succeed* (#227).** `aw_all_impls` answers "is this a loadout name" and says nothing whatever about what the current repo has, so a pin that passed that one check was accepted while describing a loadout that is not there. Every value downstream was then derived from the pinned **name** instead of from reality.

  In `bin/task-config set` — live on main since #219 — that meant `set tracker notion --impl kiro-gh` on a `claude-gh` repo computing `current=kiro-gh`, removing kiro-gh's (nonexistent) artifacts, and installing `kiro-notion` **beside** the untouched `.claude/gh-workflow.md`. Two loadouts configured: precisely the ambiguous state `task-config` exists to prevent, and the one every dispatcher hard-errors on. In the new `bin/task-remove` it meant walking a loadout that is not there, removing nothing, and still printing `task-force removed from <root>` — and for #220's strip-before-a-PR case that success line is the only thing a user checks, so they ship every artifact they meant to strip. Same failure class as #194's empty check list and #182's filter that failed open: correct-looking output for work that never happened.

  New `aw_require_configured` in `lib/detect-impl.sh` refuses the pin, naming what *is* configured here. Applied unconditionally in `task-remove` and at the top of `task-config`'s `cmd_set`, before the match count is read or `current` derived from it. `cmd_show` deliberately keeps describing rather than refusing: its contract is that it never refuses — zero loadouts and two are both *described* — it mutates nothing, and it is the command you reach for precisely when a repo is confusing, so a refusal would break the one thing that makes it useful. That asymmetry is pinned by a test so it reads as a decision rather than as the guard having been forgotten.

  But describing is not the same as asserting, and `show` was doing the latter. With no workflow doc to read, `tf_tracker_extract` returns nothing and the `tracker` line falls to its else branch: `tracker   : gh  (unset — fill in .kiro/steering/gh-workflow.md)`. That does not read as "this loadout is not here" — it reads as "kiro-gh *is* configured, someone just hasn't filled in the values", an affirmative invitation to go edit a file that does not exist, in the one command whose whole job is telling you what is configured. So `show` now annotates the loadout line — `loadout   : kiro-gh  (NOT configured here — pinned via --impl / $AW_IMPL)` — which keeps the never-refuse contract, mutates nothing, and removes the fiction. The annotation is derived from the workflow doc's *absence* rather than from the pin, which makes it structurally impossible for a loadout that really is configured rather than merely unlikely: a detected match is by definition one whose doc exists.

  And it now **exits non-zero**, which is the point `show`'s own contract already made and this case alone was breaking. The documented rule from #219 is describe-but-signal — "a repo with no loadout and a repo with two are both described rather than rejected (both still exit non-zero)" — so an unconfigured pin is the third instance of exactly that state, and was the only one returning 0. `task-config show --impl X && do_something` therefore proceeded on a phantom: the same success-signal-for-work-that-did-not-happen shape as the `--impl` bug above. Nothing depended on the old status — every reference to `task-config show` across `bin/`, `lib/`, tests and docs is human-facing prose, with no `if` and no `&&` chaining — so bringing the third case into line with the written rule cost nothing. Status and annotation are driven by the same doc-existence test, so the line printed and the status returned cannot drift apart. The `tracker` line's `unset — fill in <path>` is deliberately left as-is: with `NOT configured here` directly above it, it reads as where the file *would* go rather than as an invitation.

  **Root cause, and why it was the same bug twice:** `_collect_matches` was duplicated **byte-for-byte** across `bin/task-config` and `bin/task-remove` with no `# region:` sentinel in either file and no `tools/check-drift.sh` manifest entry — the repo's own rule is to extract rather than copy a second time. So it is extracted, to `aw_collect_matches` / `aw_impl_list` in `lib/detect-impl.sh` beside the `aw_all_impls` / `aw_detect_matches` it was already calling; there is now one copy rather than two guarded ones, and `task-config`'s and `task-remove`'s local `_impl_list` duplicates go with it.

  One further defect found while testing the fix, and worth stating because the shape is a trap: `aw_detect_matches "$root" | grep -qFx "$pin"` is wrong under `set -o pipefail`, which every caller sets. `grep -q` exits the instant it matches, so a producer writing one line per item takes `SIGPIPE` on its *next* write and `pipefail` reports the pipeline as failed **even though the match succeeded**. It therefore misfires only when there are two or more items and the match is not the last one — that is, exactly in the ambiguous repo `--impl` exists for, which is how the first version of this fix refused a pin that was genuinely configured. New `_aw_list_has` reads the list from a here-string instead, and **all three** call sites in the file use it — `aw_detect_impl`'s included, where the producer is `aw_all_impls` and the shape could not actually fire: seven names in one `printf`, far smaller than the pipe buffer, so `grep -q` can never exit before the write completes. It was converted anyway. "Works by accident of buffering" is not a property to leave in a file every dispatcher on all seven loadouts sources, the trigger is not size but someone later making `aw_all_impls` emit per line — at which point every dispatcher starts rejecting valid impls — and one shape everywhere means nobody has to work out which of three call sites was the safe one.

  Reviewer and PM note, recorded because the miss is instructive: this exact line was reviewed during #226 and signed off as "equivalent to the old case statement", on a check of fixed-string and whole-line matching semantics. Both were right; neither covers `pipefail`.

- **Radio auto-submit is its own flag on claude, no longer a side effect of `--permission-mode auto` (#246).** `task-work --auto` set both, so a worker could not get its mail submitted without also auto-accepting edits. The reverse was worse: a worker kept off `--auto` because its task is destructive (a release cut that tags and publishes) lost auto-submit as a side effect, so the worker you were supervising most carefully was the one whose handoffs stalled. The coupling stays out of sight while workers are busy, because a busy recipient's mail is drained by the Stop hook with no keystroke. It shows up the moment they go idle waiting on a review, which is exactly the handoff that matters.

  **The split, matching kiro (#206) and `task-pm` (#189):** every `task-work` copy now takes `--auto-submit` and `--no-auto-submit`. `--auto` keeps its meaning and becomes shorthand for auto permission mode plus `--auto-submit`, so existing invocations and docs behave as before. `--no-auto-submit` wins over `--auto` in either order, and `--auto-submit` composes with `--plan`. The flag arms live in a new `auto-flags` drift region shared by all seven copies, and the resolution sits in the existing `radio-env-injection` region, so the claude and kiro copies cannot drift apart again. On `task-reviewer`, `--no-auto` now drops **only** the permission mode: auto-submit stays on by default, with `--no-auto-submit` as its own opt-out. `task-recreate-worker` gains the same pair.

The documented #229 repair runs from a shell that never had the launch env, so it used to bring the role back without auto-submit for the rest of its life. That happened to the PM after a machine restart in the session that produced this issue. To make inheritance apply only to a repair, every launcher now states its choice: `task-work`, `task-reviewer` (both loadouts) and `task-pm --no-auto-submit` export `TASK_FORCE_AUTO_SUBMIT=0` instead of leaving it unset. `task-recreate-worker` is the one exception. With no flag it injects nothing on purpose, so a rebuilt worker keeps the setting it had before it died. gc sweeps the new sidecar together with the other two.

A throwaway checkout of `origin/main` at `454c713` measures 1379/1379, so this change adds 16 tests. `tools/check-drift.sh` goes from 25 to 26 groups (the new `auto-flags` region). - **`task-recreate-worker` — recover a worker whose tab died but whose worktree survived (#230).** A machine restart kills every role on the box at once: on 2026-09-28 that was ten clean `unregister` lines in one second across four repos. None of the *work* was lost, because none of it lives in the tab — the worktree and its branch, `task-work`'s `<worktree-base>/.<slug>.info` sidecar, radio's `<role>.loadout` / `<role>.agent` sidecars (#188) and the role's mailbox all sit on disk and come back untouched. What dies with the zellij server is the tab, the radio session file, and `$TASK_FORCE_ROLE` (#229). Nothing in the toolset covered getting back in: `task-work <slug>` refuses because the branch and worktree already exist, which is correct and which #38 made a hard stop on purpose; `task-done` is the opposite operation. So the recovery was a hand-rolled tab, a `cd`, a guess about resuming, and a session radio had no name for — the worker on #223 was rebuilt exactly that way, finished the work, opened PR #228, and could not deliver its report to PM.

  The new command is a **re-binding**, not a re-creation. It opens a fresh zellij tab on the existing worktree and launches the agent with the same role env `task-work` injects, which is the entire point: `SessionStart` registers the role, so the worker is wakeable again and its next report goes out as itself rather than `from: unknown`. Before launching it prints what it found — the issue URL and base branch off the sidecar, commits ahead of base, whether the branch was ever pushed, whether a PR already exists, and how much mail queued while the role was offline. Dead-lettered mail is counted **separately** and flagged, because a register will not redeliver it (#201) and the count would otherwise read as backlog that is about to be drained.

  **It never creates, reuses or removes a worktree.** A missing worktree is new work, so it refuses and names `task-work` — the two commands must not overlap, and silently recreating the tree would hand the rebuilt worker an empty checkout while the branch's contents went unmentioned. It also refuses a directory that is not a registered worktree *of this repo*, a detached HEAD (nothing downstream can open a PR from one), and a `review-pr<N>` slug, which is a reviewer: single-shot, self-cleaning, its analysis in the PR comment rather than the tab, and its role named `reviewer-<repo>-pr<N>` — relaunching `/worker` there would both run the wrong agent and mint a role nothing addresses. The digits are matched rather than the prefix, so `review-print-flow` stays a worker, the same test radio's own role recovery uses.

  **Fresh is the default and `--resume` is the opt-in**, in that order deliberately. A fresh session's register-time backlog drain (#168) puts the queued handoff in front of the agent on its first turn, and its role env is right from the start. `--resume` is for uncommitted exploration worth keeping. It recovers the session id from the `SessionEnd` payload radio logs on an unregister — the reboot that killed the tab usually did fire one — but treats it as a hint and not a mechanism: the log self-rotates past ~1MB (#169), a hard kill fires no `SessionEnd` at all, and a role that has run several times has several lines. So the match is pinned three ways before the id is used: the role, the payload's own `cwd` (this exact worktree, not another checkout of the same repo), and a transcript file that still exists. Anything short of all three falls back to Claude's own picker **and says which happened**, because silently resuming the wrong session is far worse than an interactive prompt. The `cwd` pin matches the worktree's **physical and logical spellings both**: the worktree path is built by string-appending `<repo>-worktrees`, which resolves nothing, while Claude records the directory it actually ran in — so one symlink under the worktree base (worktrees parked on another volume, say) would make a single-form match miss every time. That does not fail safe, it fails *invisibly*, leaving `--resume` looking present while it silently always fell through to the picker — the one outcome a load-bearing pin must not have. Both forms are matched rather than one replaced by the other, since the log is history and a line written before a path change legitimately carries the other spelling. The same divergence made the worktree check compare a logical path against git's physical one and refuse a perfectly good worktree as "inside another repo's worktree"; every path comparison in the command now resolves both operands. Claude-only; kiro is refused by name rather than launched into something that looks like a resume and is not.

  **It refuses when the role still looks live**, on either of two independent signals — a zellij tab of that name is open in this session, or the session file's heartbeat is newer than an hour. Staleness is asked of `radio orphans` rather than re-derived, so the threshold and the GNU/BSD date parsing stay in one place. Both signals are checked because either can be true alone, and the first hour after a reboot looks *exactly* like a live session — which is why that refusal has a documented way through (`--force`) and names which signal fired instead of just saying no.

  **The stale `TAB_ID` is the trap this had to be built around.** zellij's server restarted, so the id still in the sidecar is either absent or now belongs to an unrelated tab — and since #218 `radio register` *recovers* `TAB_ID` from that same file when its own name lookup misses, so a naive re-register adopts it. #167's verify-name-at-id check would catch it on the send path; relying on that would be building on someone else's backstop. So the id is stripped **before** the tab is spawned and the new one written after: if the rebuilt session's `SessionStart` wins the race, it finds nothing to adopt and falls through to the name lookup, which by then resolves to the tab we just made. The ordering is pinned by a test that fails the `new-tab` call and asserts the sidecar is already clean at that point. While rewriting the file it also **ensures `SLUG=` is present**, recreating a missing sidecar outright — that line is what radio's roleless role-recovery keys off (#229), so a worker whose sidecar was lost would otherwise be unrecoverable a second time.

  Canonical single copy like `task-pm` and `task-reviewer` (#170): only the final launch line differs by agent. Every loadout installer links it.

  **Upgrading: re-run the loadout's `install.sh`** to get the `task-recreate-worker` symlink into `~/.local/bin` — `task-init` does not create symlinks, so a `task-init` re-run alone leaves the command missing. Re-run `task-init <loadout>` as well to refresh the workflow doc's managed region with the new section; nothing else installer-written changed.

- **`task-remove` — take task-force back out of a repo (#220).** There was no supported way to undo an install. Two situations want one. The project is done and the workflow config is dead weight; or — the one that actually stings — you `task-init`'d a repo that does *not* use task-force so you could work in it, and the PR diff would otherwise carry `.claude/commands/`, a `settings.json` hook merge, a `CLAUDE.md` import line and a workflow doc the upstream maintainer never asked for. The existing workaround for that (commit `task-init`'s output as one commit, `git revert` it before opening the PR) is cheap and exact and still works; it degrades once anything else has touched `.claude/settings.json` since that commit, or when the init was never isolated into a commit in the first place.

  `bin/task-remove` is a thin wrapper over the removal engine #219 landed in `lib/loadout-artifacts.sh` — `la_owned_paths` for the inventory, `la_plan` / `la_remove` for the walk, whose **single** code path for plan and apply is why a `--dry-run` cannot lie about what the real run does. Canonical rather than dispatching, for `task-config`'s reasons: it acts across loadouts and has to keep working when detection is ambiguous. `--dry-run` prints the plan and changes nothing; a TTY run previews and asks; `--yes` skips the prompt; `--impl <name>` narrows to one loadout. Without `--impl` it removes **every** loadout it detects, because "take task-force out" means all of it and leaving one behind is the multi-match state every dispatcher refuses on.

  Two things the engine did not already cover. The **`commit-msg` ci-guard hook** `task-work` installs (#194) is removed, and where the chain-install preserved a pre-existing hook as `commit-msg.local` that name is put back — the exact inverse of the install. Only a hook carrying task-force's own marker is touched, so a `commit-msg` of yours (or husky's, via `core.hooksPath`) is named and left alone; the hooks directory is resolved through the installer's own `aw_ci_guard_hooks_dir`, so the two cannot disagree about which file is even in play. Git shares one hooks directory across every worktree of a repo, so this is a repo-wide removal made from whichever worktree you are standing in, and the run says so. It is deliberately outside `_la_walk` and unreachable from a loadout switch: the guard is task-work's, is not per-loadout, and a repo moving from claude to kiro still wants it.

  And **`--purge`**, the answer to the one question #220 left open. #219's keep-bias — a role file that does not byte-match the shipped copy is kept and reported, never deleted — is correct, and it is also imprecise in one direction worth naming: it fires on a merely **stale** install too, not only on a real customization, because a repo set up from an older checkout has role files that no longer match what the current checkout ships. For a `task-config set` that is cosmetic residue. For `task-remove`'s second use case it is a file in the diff a maintainer reads, and so is the `<doc>.bak` the workflow-doc removal leaves behind. `--purge` deletes what the default would keep: a role file that differs from the shipped copy, the `<doc>.bak` (the one this run would have written, and any an earlier run left beside the doc), and the `tasks/` backlog — "the project is done" being a real reason to want that gone. The default is **not** inverted: what was missing was informed consent, not a different bias. So the plan lists kept files as distinctly as removed ones, and the run points at `--purge` only when there is something it would actually take — matched against the three things the flag really flips rather than any "kept" line, so it is never offered for the commit-msg hook it would not touch either way. What `--purge` does *not* do is widen removal to files that are only partly ours: `CLAUDE.md` still loses only its import line, and a `settings.json` full of your own hooks still keeps them. It changes what counts as task-force's, not what counts as yours. Threaded through as `LA_PURGE` rather than a new parameter precisely so plan and apply stay one body.

  **Scope is per-repo, and the boundary is load-bearing.** The `~/.local/bin/task-*` symlinks and the shell-rc `PATH` line are the *global* install, shared by every repo on the machine — removing them because one project ended would break every other project, so a `--global` flag is a separate ask. Live worktrees and `~/.task-force` radio state are out too: `task-done --remove-worktree` already owns worktree teardown and mailbox sweeping. The run prints that boundary every time, because "it didn't happen" is not something you can otherwise see in the output. A repo with no loadout exits non-zero with a message rather than a crash — and if the ci-guard hook is still installed there, its path is named, since that is the one artifact that outlives a workflow doc someone deleted by hand and the only thing still acting on commits in a repo that looks clean.

  `tests/task_remove.bats` (40 tests) asserts zero artifacts left on **all seven** loadouts by reading the path inventory out of `la_owned_paths` itself rather than restating it, so the test and a wrong implementation cannot drift into agreeing; that a `--purge` run on a virgin repo returns the tree to its pre-init checksum byte-for-byte; that a pre-existing `CLAUDE.md`, a `settings.json` with the user's own hook / `deny` / `model`, a command of their own and a `tasks/` backlog all survive, while a `settings.json` task-init created from scratch is deleted; each `--purge` case including the swept `.bak`; the commit-msg hook's removal, its `commit-msg.local` restore, and a foreign hook being left alone; `--dry-run` inertness by tree checksum with the hook asserted separately since `.git` is pruned from it; that the plan predicts exactly the removals the real run performs; and — the dangerous direction, asserted explicitly rather than left to "no test exercises it" — that nine `~/.local/bin` symlinks and the shell rc come out of a `--purge --yes` run untouched. Two more cover the `--impl` refusal below, through the flag and through `$AW_IMPL`. `tests/install_symlinks.bats` covers the new link on all seven installers.

  Upgrading: **re-run `./install.sh <loadout>`** to pick up the `~/.local/bin/task-remove` symlink. Re-run **`task-init <loadout>`** as well if you want the new `task-remove` section in your repo's workflow doc — nothing else self-applies, and no existing artifact's behaviour changed (`task-config set` is unaffected: it never sets `LA_PURGE`, so it cannot reach any of the new deletions).

- **`task-config` — ask a repo which loadout it is on, and switch its assistant or tracker without stranding the old one (#219).** Two questions had no supported answer. *Which loadout is this repo on, and what tracker settings does it carry?* was inferable only by knowing which seven paths to stat. And *switch this repo from claude to kiro* meant running `task-init <new-loadout>` and then hunting the old loadout's artifacts by hand — its workflow doc, `commands/` or `agents/` (+ the pre-#218 `hooks/`), the `CLAUDE.md` import line, the radio hook entries and seeded allow-list inside `.claude/settings.json`, and `tasks/` on the `*-local` loadouts. Miss one and the repo is in the state `aw_detect_impl` hard-errors on, so *every* dispatcher starts refusing with a multi-match error; the failure surfaces at the next `task-work`, not at the switch.

  `task-config show` prints the assistant, the tracker, that tracker's settings and the paths carrying them. It is the one task-force command that never refuses: a repo with **no** loadout and a repo with **two** are both *described* rather than rejected (both still exit non-zero), and the ambiguous case names every match — which is precisely what `Error: multiple agentic-workflow impls detected` would not tell you.

  `task-config set assistant <claude|kiro>` / `set tracker <gh|jira|notion|local>` / `set loadout <name>` run the same five steps: detect the current loadout, carry the tracker settings off its workflow doc, remove that loadout's artifacts, **delegate the install to `<new-loadout>/bin/task-init --force`** with the carried settings, report what moved. Step 4 is a delegation on purpose — `task-init` already knows how to render every template, preserve placeholders and merge hooks idempotently, and a second implementation here would be a second thing to keep in step. `--dry-run` prints the plan and changes nothing (one code path serves both modes, so a dry run cannot lie about what the real one does); a TTY run confirms first and `--yes` skips it; `--impl <name>` says which loadout to replace in an ambiguous repo. `kiro-jira` is refused by name, because the assistant × tracker grid has exactly one hole (#92) and the honest way to know is to look on disk.

  Removal is the **inverse of task-init's idempotent merge** (#183, #212): it takes out only task-init's own entries and deletes a file only when nothing else was in it. A `CLAUDE.md` full of your own instructions survives with just the `@.claude/<t>-workflow.md` line gone; a `settings.json` carrying your own `Stop` hook, allow entries, `deny` and `model` survives with just the radio-owned hooks and the seeded literals gone; a `.gitignore` loses only `.git/task-force/`; a command or agent of your own beside the role files is never touched *and keeps its directory*; and on the local loadouts the `tasks/` scaffolding goes while **your backlog stays**, with the run reporting how many files it kept. Directories are reclaimed only once removal has actually emptied them. One accepted imprecision: the seeded allow-list is matched as a literal set, so a permission you independently wanted *and* task-init also seeds (`Read`, `Bash(ls *)`) goes away with a switch — `--dry-run` is the mitigation, and a provenance manifest was weighed and rejected because `task-config` only ever removes one *named* loadout's artifacts, never "everything task-init ever did here".

  The **role files** get the most care, because they are the likeliest place a switch could destroy work. `task-init` installs `.claude/commands/<role>.md` and `.kiro/agents/<role>.json` through `install_file`, whose `keep` / `prompt` policies let an existing file survive a re-run — and on kiro it then merges the radio hooks *into* whatever survived (#218, #222), so an agent config can be your work carrying our entries. So removal never deletes a role file it cannot prove is task-init's own. A kiro agent config has its radio hooks stripped first — the exact mirror of the install merge's `startswith("radio ")` guard, so a non-radio hook of yours on the same trigger survives — and is deleted only if what remains still matches the shipped copy; a customized one keeps your edits and loses only our hooks. A claude command file is deleted only on a byte-identical match with the shipped copy, and otherwise kept with a line saying why. The bias is deliberate: a file that no longer matches, whether because you edited it or because the checkout has moved on since you installed, is kept and reported rather than removed silently.

  The **workflow doc** is the one file that goes regardless — it is the detection key, and leaving it is the multi-match state all of this exists to avoid. But #183's promise is that everything below the managed-region end marker is yours, so when there is anything of yours down there the doc is copied to `<doc>.bak` first (through `managed-region.sh`'s own backup-path helper, so a second switch never clobbers the first backup) and the run says where it went. A doc carrying only task-init's stub tail is deleted without a backup. That backup is also why `_la_dir_empty_after` takes a *created*-paths set alongside the removed one: without it the plan promised to reclaim `.kiro/steering/` while the real run correctly left the `.bak` sitting in it — a dry-run over-promising is exactly what sharing one code path is supposed to rule out.

  Settings carry across a `set assistant` and cannot across a `set tracker`. claude and kiro render the same template shape per tracker, so `owner` / `repo` / `project` move over cleanly on a gh repo; different *trackers* share no fields at all, so there is nothing to carry and `task-init` prompts exactly as on a first install. That asymmetry is correct rather than a gap, and is documented as such in the README and all seven `steering/*-workflow.example.md` templates.

  **Known limitation, notion:** carry-over works by handing `task-init` the old values as flags, and the notion loadouts have **no settings flags** — only `--force` / `--restore` / `--workflow` / `--commands` / `--hooks` / `--help-ids`. So `show` reads and prints a notion repo's database IDs, but a `claude-notion ↔ kiro-notion` switch cannot carry them and you must paste them into the new doc yourself. It is the worst tracker for that, since the IDs are opaque strings no URL yields — the reason `--help-ids` exists (#9). Stated explicitly in the README and in both notion templates rather than left implied by absence, because a user needs to know *before* they run the switch. **#225** adds the flags, after which notion carry-over works through this same code path with no change to `bin/task-config`.

  Three pieces of structure came out of it. `task-config` is a **canonical** script (`bin/task-config`, linked by all seven installers from the drift-guarded `install-shared-symlinks` region), not a dispatcher into `<loadout>/bin/`: it acts *across* loadouts, has to know about one the repo is not on, and has to keep working when detection is ambiguous. New `lib/loadout-artifacts.sh` holds the enumeration + removal engine, factored out rather than inlined because `task-remove` (#220) is its second consumer. New `lib/tracker-settings.sh` holds the settings table — field, flag, placeholder and extraction regex per tracker — replacing the per-loadout `_preserve_placeholders` copies in `claude-gh` / `kiro-gh` / `claude-jira`'s `bin/task-init`; `task-config` now reads a rendered doc through the same regexes that wrote it, guarded by two new `tools/check-drift.sh` regions. `lib/detect-impl.sh` grew `aw_all_impls` / `aw_impl_workflow_doc` / `aw_detect_matches`, so the list of loadouts and the doc-path mapping live in one place instead of being hard-coded per caller, and `aw_detect_impl` now scans through them.

  Also fixed along the way, in the jq that strips the allow-list: `$seeded | index(.)` asks whether `$seeded` contains *itself*, because jq evaluates `index(f)`'s argument with the piped input as `.`. It is true for every entry, so the first version of this silently deleted the whole allow-list including the user's own entries. `tests/task_config.bats` (49 tests) covers `show` on all seven loadouts, both refuse-worthy states, the `claude-gh → kiro-gh → claude-gh` round trip with zero stray artifacts, user-content survival, the no-carry-over path, the `kiro-jira` refusal, `--dry-run` inertness by tree checksum, that the plan predicts exactly the removals the real run performs (including the backup case), and the role-file dispositions — a customized agent config keeping its edits, a user hook on the same trigger surviving, a pristine one still going, a customized claude command being kept, and the workflow-doc tail being backed up — plus two tests aimed squarely at the `index(.)` bug — that every user-authored allow-list entry survives (including adversarial ones like `Bash(gh workflow run *)` and `Bash(ghost *)`, which share a prefix with seeded gh literals without being any of them) and that the documented imprecision is asserted rather than merely written down — and a lockstep check that `la_seeded_allow` still matches the literals each `task-init` seeds.

  Two smaller things fell out of testing the confirmation prompt on a real terminal. `read` at that prompt is now guarded, so EOF (the terminal going away mid-question) reads as "no" instead of exiting with `read`'s own status and no explanation — under `set -e` that is the difference between `Aborted; nothing was changed.` and a bare failure after the plan was printed. And `pty_run` in `tests/helpers/common.bash` takes an optional second argument: text to feed the pty as the child's stdin, so a `read` prompt can actually be answered from a test. Piping it in naively does not work — when the writer closes immediately, BSD `script` pushes `^D` into the pty *ahead of* the bytes it buffered (the pty echoes `^Dy` and the child's `read` returns empty), so the helper holds the pipe open past the write to order the data before the EOF. `tests/pty_helper.bats` covers both the new form and the unchanged EOF-at-once one.

  Upgrading: **re-run `./install.sh <loadout>`** to pick up the `~/.local/bin/task-config` symlink. Re-run **`task-init <loadout>`** as well if you want the new `task-config` section in your repo's workflow doc — nothing else in this change self-applies, and no existing artifact's behaviour changed.

New `tests/radio_runbook.bats` (12 tests) pins the block identity within each group, the #177 neutrality, the claude/kiro asymmetry, and — the load-bearing one — that **every log string the runbook tells you to grep for is a literal substring of `bin/radio`**, so a rename there fails the suite instead of quietly turning the runbook into a page of commands that match nothing. The flapping row names **both** causes of a `role=` / `proceeding` gap rather than only the stale-binary one: `--manual` short-circuits the block that emits *both* the `skipping` and `proceeding` lines, so it writes `unregister role=` alone, and anything calling it in a loop inflates that counter by itself — which is precisely what #205 found (an unisolated test suite unregistering the developer's live role 57× per run) and what a stale-binary-only diagnosis would have misread. *Upgrading: re-run `task-init <loadout>` in each configured repo to render the runbook into `.claude/<loadout>-workflow.md` / `.kiro/steering/<loadout>-workflow.md`; an already-filled-in workflow doc is yours to edit and is never overwritten without `--force`, so copy the section across by hand if you have customised yours. Docs only — no behaviour change, and `bin/radio` is untouched.* (#191)
- **New `radio gc` prunes the radio home — dead mailboxes, expired processed messages, an oversized log — and it runs automatically (throttled) on a fresh `register`.** `~/.task-force/radio/mailbox/` accumulated one directory per role forever: hundreds of long-dead workers/reviewers, many holding undelivered messages (an `approved-and-merged` sent after the tab closed), plus a literal `--tab` directory from a historical malformed register — and the top-level `log` grew unbounded (450KB and climbing in the live tree). Nothing ever pruned any of it. `radio gc [--dry-run] [--max-age-days N]` (default N=14) now reclaims an entire `mailbox/<role>/` only when **all three** hold: the role is **dead** (no session file, OR a >1h-stale `LAST_HEARTBEAT` — the same threshold `radio orphans` / `cmd_send` use and #127 self-heals, so a crashed worker's lingering `.info` no longer makes its mailbox immortal), its **inbox holds no unread mail**, AND its newest surviving entry has aged past the cutoff (a brand-new empty mailbox is protected by falling back to the *directory's* own mtime, so a register-in-flight race can't sweep a live role). The **empty-inbox gate is load-bearing**: it stops gc from destroying undelivered mail — notably the ~64-message legacy `pm` backlog that **#182** is deferred to adopt (post-#165 nothing registers as literal `pm`, so its inbox is write-only until then); a dead role still holding unread mail falls through to the processed-only sweep, which never touches inbox. Surviving roles get their `processed/` messages older than the cutoff expired; an unreadable file mtime is treated as *now/protect*, never epoch-0/ancient, so a transient `stat` hiccup can't delete live mail. `log` is rotated to its last ~512KB once it passes ~1MB. `--dry-run` reports every action (`[dry-run] remove dead mailbox: …`) touching nothing on disk. The sweep is **amortized** onto `cmd_register`: a fresh primary `SessionStart` runs a quiet 14-day gc, **throttled to once per hour** via a `.gc-last` sentinel so a fleet of `--auto` workers re-registering within seconds don't each re-walk the global mailbox tree (gated on `fresh=1` so `/compact` / resume re-registers don't re-sweep, output suppressed so it can't pollute the #168 drain summary) — no cron needed. Two companion hardening beats: `_validate_role` now rejects a **leading `-`** (killing the `--tab`-style flag-swallowing artifact class at the source — `radio send --to --tab …` / `radio register --role --tab …` now fail validation loudly), and `task-done --remove-worktree` sweeps its own role's mailbox on cleanup (the role is dead by definition once its worktree and tab are gone), guarded against empty/traversal role names so a stray env value can never `rm -rf` the mailbox root. Lands across `bin/radio` and the `task-done-std` + `task-done-local` drift groups (7 binaries); `tests/radio_gc.bats` covers the sweep, TTL, the #182 unread-inbox guard, stale-heartbeat reclaim, dir-mtime protection, dry-run, log rotation, the register piggyback + throttle, and leading-dash rejection. No `task-init` re-run needed — `radio` and `task-done` are shared symlinks from root `bin/`, refreshed by `git pull`. (#169)
- **The PM is now a per-repo role (`pm-<reponame>`), so two PMs in two repos no longer clobber each other — with a registration-gated `--to pm` shim, launch-time `$TASK_FORCE_PM_ROLE` injection, and `task-pm --also` for one PM overseeing N repos.** Workers and reviewers were already repo-namespaced (`worker-<reponame>-<slug>`, `reviewer-<reponame>-prN`) but the PM was the literal global role `pm`: a second `task-pm` in another repo overwrote `~/.task-force/radio/sessions/pm.info` (last-register-wins), so wake-ups went to the newest PM tab regardless of which repo the sender belonged to; every repo's reports mixed in one global `pm` inbox; and when no PM ran anywhere, reports queued silently (the July logs: 35 `no session for pm` failures). `task-pm` now derives the **main-repo** name (`git rev-parse --git-common-dir`'s parent, so it's worktree-proof — `basename $(git rev-parse --show-toplevel)` is the *worktree slug* inside a linked worktree — and sanitized to radio's role charset so `my.app` yields the valid `pm-my-app`), exports `TASK_FORCE_ROLE`/`ZELLIJ_TAB=pm-<reponame>`, and renames the tab to match, failing fast before touching the tab if the name is unusable. **`--to pm` is the stable wire format** (every `/planner` / `/worker` / `/reviewer` prompt sends exactly that), and the env var is consumed *inside* `radio send`, registration-gated, so a new worker can't strand a ping at an unregistered `pm-<repo>` while a live PM waits. The shim resolves, each step winning only when its target is actually registered: (1) `$TASK_FORCE_PM_ROLE` — injected launch-time identity by `task-work` (all 7 loadouts, drift-guarded `radio-env-injection` region) and the claude `task-reviewer`; (2) derive from the sender's own identity — a persisted, worktree-proof `REPO_NAME=` (falling back to `basename(REPO=)` for old sessions), else the **longest** matching live `pm-<name>` (deterministic, not glob-order-dependent); (3) literal `pm` if a pre-migration `pm.info` still exists; (4) queue at the best future address so the no-session WARNING names where a PM should register. The resolution is logged and named on stdout on every shim invocation (`radio: --to pm → pm-mapolygon (via $TASK_FORCE_PM_ROLE (registered))`) — the observability handshake with #166. **Multi-repo PM via alias sessions:** `task-pm --also <repo-path-or-name>` (repeatable; paths validated + resolved against the invocation cwd, unknown flags rejected) writes a `pm-<other>.info` carrying `ALIAS=pm-<primary>` and no inbox of its own; `radio send` follows exactly one alias hop (a second is refused, exit 2) so a `--to pm-<other>` lands in the primary's single inbox and wakes its tab — one PM brain, one inbox, N repos (zero-config fallback: one `task-pm` per repo in separate tabs). Aliases self-heal: they're recorded in a primary `.aliases` sidecar and re-seeded on every `register`, so a `/compact`, restart, or an erroneous unregister sweep doesn't silently drop multi-repo routing; a pre-existing `pm-<other>` inbox is migrated into the primary at alias creation; the primary's real exit sweeps its aliases and drops the sidecar; and `radio orphans` flags an alias whose target session is gone. **Basename-collision warning:** `radio register` warns (log + stderr, non-blocking) when a role is re-claimed for a different repo — comparing canonical repo *roots*, so worktrees of one repo don't false-alarm while two repos both named `api` do. Scope: claude-* loadouts for the prompt/doc changes (kiro parity is a follow-up; kiro workers still route correctly via the injected env + shim). New `lib/repo-name.sh` (`aw_main_repo_name`) and `radio register-alias` subcommand back the feature. Draining the pre-existing literal-`pm` backlog post-migration is a tracked follow-up. **Upgrading**: re-run `task-init <loadout>` in each configured repo to refresh the `/planner` / `/worker` / `/reviewer` prompts in `.claude/commands/` — *recommended, not required*: the wire format (`--to pm`) is unchanged from pre-#165, the shim resolves it correctly, and `radio` / `task-pm` / `task-work` are shared symlinks from root `bin/` (no hook or settings change). (#165)
- **The `/worker` prompt now carries a pre-PR checklist — the recurring review findings from the radio bundle are caught before review, not during it.** Four consecutive radio PRs (#172–#175) drew the same review classes: a missing or incomplete CHANGELOG entry (3 of 4), a missing README/steering doc beat for a behavior change (3 of 4), re-implementing a helper the codebase already had (2 of 4), and skipping instructions left as comments on the spec issue (1 of 4). Each claude `commands/worker.md` (gh / jira / notion / local, plus this repo's dogfooded `.claude/commands/worker.md`) gains a five-item checklist between the commit step and PR creation, to walk before radioing `review-requested`: add a changelog entry if the repo keeps one, a docs beat for user-visible changes, a reuse grep before writing scaffolding, a re-read of the spec in full (including comments/notes added after the body), and a green-suite + linters + consistency-checks + `gh pr checks` gate. The checklist is deliberately **repo-generic** — `worker.md` ships downstream verbatim via `task-init`, so it names no file that only exists here and cites no bare issue numbers (which would resolve to a downstream repo's own PRs); this repo's specifics (`./run_tests.sh` + `tools/check-drift.sh` + `shellcheck -x`, the keepachangelog + `task-init` Upgrading convention, the `steering/*.example.md` doc beat, the #163/#164/#168 precedent) live in `.claude/gh-workflow.md`, the per-repo file `task-init` already templates. The checklist block is byte-identical across gh / jira / notion (and the `.claude` dogfood copy); claude-local adapts the spec item to its comment-less `tasks/NNN-slug.md` files. A `tests/worker_checklist.bats` guard enforces the dogfood parity and the repo-generic invariant (no task-force-only paths, no bare `#N`). Kiro worker agents are a deliberate follow-up, tracked in #178. **Upgrading**: re-run `task-init <loadout>` in each configured repo to pull the updated `/worker` prompt into `.claude/commands/`; without it the repo keeps the old prompt. (#176)
- **`task-work --auto` spawns the worker tab without stealing focus from the caller.** Zellij's `new-tab` has no `--no-focus` flag, so dispatching a worker from PM always snapped focus into the new tab — friction when running 3–4 parallel `--auto` workers back-to-back. `aw_launch_tab` now takes an optional `stay_on_caller_tab` arg; `--auto` task-work threads `$AUTO_MODE` through so the launcher captures the caller's tab position via `zellij action list-tabs --json` before `new-tab`, then snaps focus back with `go-to-tab <pos+1>` after. Default `task-work` and `task-work --plan` are unchanged — both still land in the new tab (planner is interactive; you want to be there). Defensive: all gates (`$ZELLIJ` unset, `jq` missing, empty position, non-zero `go-to-tab`) fall through to the legacy focus-shift path; the worker spawn never aborts because the snap-back failed. (#130)
- **Opt-in auto-submit on radio wake-up for `--auto` workers.** `radio send`'s zellij `write-chars` wake-up has always written `radio check\n` (LF) into the recipient's pane, leaving it sitting in the input box until the user pressed Enter. For workers launched via `task-work --auto` — already an explicit autonomy opt-in, and idle most of their life waiting on PM — that human gate is friction with no upside. `task-work --auto` now exports `TASK_FORCE_AUTO_SUBMIT=1`; `radio register` / `_ensure_session_file` persist that as `AUTO_SUBMIT=1` in the session file; `cmd_send` reads it and switches the wake-up byte to CR (`\r`), which Claude Code's raw-mode input binds to Enter. PM and default (non-`--auto`) workers leave the flag unset and keep the LF wake-up, so a `radio check` ping can never corrupt a partially-typed prompt. (#128)

## [0.2.2] — 2026-05-23

Patch release. Extends the cross-tab targeting fix from `v0.2.1` (radio) to `task-done`, and hardens the radio session lifecycle so intra-session Claude events (`/clear`, `/compact`, resume) don't brick subsequent radio operations.

### Fixed

- **`task-done` close-tab no longer targets the focused tab.** The final `zellij action close-tab` in `*/bin/task-done` had no explicit tab id, so if the user switched focus to another tab (e.g., PM) while a worker was auto-cleaning up, the wrong tab got closed — destroying the user's active session. Same root cause as #102, in a different binary. `task-done` now captures the worker's stable `TAB_ID=` from its radio session file *before* `radio unregister` runs, and closes the tab via `zellij action close-tab-by-id`. If no tab id can be captured (zellij not running, no role, missing session file), close-tab is skipped — never falls back to the unscoped call. (#107, #108)
- **Radio session file survives intra-session Claude events.** Claude Code's `SessionEnd` hook fires on `/clear`, `/compact`, and session resume in addition to real exit. The old `radio unregister` hook proceeded unconditionally, wiping the session file mid-life — observed in production as bursts of 40+ unregister calls within ~25s, with subsequent `busy`/`ready`/`send` operations logging "no session file" for the now-missing role. `cmd_unregister` now reads the JSON payload piped by the hook and skips when `reason` is `clear` or `resume`; manual `radio unregister` (no stdin payload) still works. Companion `_ensure_session_file` in `_update_state` self-heals if a stale unregister did get through. (#108)

### Internal

- New bats coverage: `tests/radio_lifecycle.bats` and `tests/task_done_close_tab.bats` pin the contract for both fixes.

## [0.2.1] — 2026-05-22

Radio polish + reliability patch. Lifecycle / UX fixes building on the `v0.2.0` radio rollout, plus a tab-targeting fix that hardens cross-tab routing.

### Fixed

- **Radio hooks no-op when `$TASK_FORCE_ROLE` is unset.** Plain `claude` in a task-force-equipped repo was getting blocked at every prompt because the `UserPromptSubmit` hook (and friends) erred out when no role was set. Hook-invoked subcommands (`busy`, `ready`, `check`, `unregister`, `register --role ""`) now silently exit 0 when role is missing; user-invoked subcommands (`read`, `ack`) still fail loudly. (#93, #96)
- **Auto-unregister radio sessions on session/worker end.** Worker session files were orphaning in `~/.task-force/radio/sessions/` after a worker finished. Two new lifecycle beats: a Claude `SessionEnd` hook calls `radio unregister`; `task-done` calls `radio unregister` before tearing down the worktree. (#94, #97)
- **Radio tab/pane actions no longer target the focused tab.** Both `_rename_tab` (idle/busy emoji prefix) and `radio send` (wake-up via `radio check`) used `zellij action` calls without explicit tab targeting, so they clobbered whichever tab the user happened to be focused on — e.g. PM's tab name got rewritten when a worker auto-unregistered, and `radio send --to pm` from worker B mis-delivered the wake-up to worker A. Now both paths drive zellij via stable tab/pane ids captured at `radio register` time (`TAB_ID=` in the session file), with `rename-tab-by-id` and `write-chars --pane-id`. Routing is name-collision-proof and survives user-driven `rename-tab`. (#102, #103)

### Added

- **Idle/busy emoji in zellij tab names.** `radio` now prefixes the current tab with `⏸️` (idle) or `▶️` (busy) so you can see at a glance which workers are mid-turn vs. waiting on input — useful when running several workers in parallel. `TAB=` in the session file is kept in sync so `radio send`'s `go-to-tab-name` wake-up still finds the renamed tab. (#95, #99)
